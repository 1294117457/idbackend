# RBAC 接口鉴权方案文档

> 目标：实现「`user -> role -> permission -> backend api`」的标准 RBAC 鉴权链路，并通过 `PermissionMiddleware` 在每次请求时完成接口级鉴权。
>
> 约束：本文仅整理方案，不修改现有代码。

---

## 1. 方案目标

本方案希望实现以下能力：

1. `permission` 绑定后端接口
2. `role` 绑定 `permission`
3. `user` 绑定 `role`
4. `PermissionMiddleware` 在请求进入业务层之前完成鉴权
5. 接口权限映射使用 Redis 缓存，提高性能
6. 权限配置变更后，主动刷新对应缓存，保证实时生效
7. 提供白名单机制，支持公开接口和系统账号放行

---

## 2. 核心设计

### 2.1 权限关系

```text
User -> Role -> Permission -> Backend API
```

### 2.2 角色与权限职责

- `user`：普通学生，只能访问自己的申请相关接口
- `reviewer`：审核员，能处理审核相关接口
- `admin`：管理员，能管理学生、模板、审核等业务
- `super_admin`：超级管理员，拥有系统级全部权限

### 2.3 权限码建议

建议使用统一格式：

```text
resource:action
```

示例：

- `user:create`
- `user:read`
- `user:update`
- `user:delete`
- `role:assign`
- `permission:manage`

如果需要更细粒度控制，也可以扩展为：

- `review:approve`
- `review:reject`
- `apply:my`
- `apply:view`

---

## 3. 中间件职责划分

### 3.1 AuthMiddleware

职责：

- 处理登录态
- 解析 JWT
- 将当前用户信息写入请求上下文
- 处理公开接口白名单
- 识别系统白名单账号

### 3.2 PermissionMiddleware

职责：

- 判断当前接口是否需要鉴权
- 从 Redis 查询接口绑定的 `permission`
- Redis 未命中则查数据库
- 数据库未配置时记录状态
- 校验当前用户是否拥有该权限
- 返回 401 / 403 / 放行

---

## 4. 请求流程

### 4.1 完整链路

```text
Request
  -> AuthMiddleware
  -> PermissionMiddleware
  -> Business Handler
```

### 4.2 详细流程

1. 请求进入系统
2. 先判断是否为公开接口
3. 若不是公开接口，则检查 JWT
4. JWT 解析成功后，写入当前用户上下文
5. `PermissionMiddleware` 读取当前请求的接口标识
6. 优先从 Redis 获取该接口对应的权限码
7. Redis 未命中则查询数据库
8. 数据库仍未命中则标记为“未配置”或“公开”，并记录日志
9. 根据当前用户的角色权限集合做匹配
10. 有权限则放行，无权限则返回 403

---

## 5. Redis 缓存设计

### 5.1 缓存内容

建议至少缓存三类数据：

1. 用户角色集合
2. 用户权限集合
3. 接口到权限的映射

### 5.2 缓存 Key 建议

- `rbac:user:roles:{user_id}`
- `rbac:user:perms:{user_id}`
- `rbac:api:{method}:{normalized_path}`

### 5.3 缓存状态建议

接口权限映射建议区分三种状态：

- `PUBLIC`：公开接口，不需要鉴权
- `AUTH_REQUIRED:{permission_code}`：需要权限校验
- `UNCONFIGURED`：数据库未找到配置

不建议仅用“空字符串”表示所有缺省情况，否则后续排查会很困难。

---

## 6. 白名单设计

### 6.1 公开接口白名单

适用于无需登录即可访问的接口，例如：

- 登录
- 注册
- 验证码
- 健康检查
- 文档接口

### 6.2 系统账号白名单

适用于超级管理员或运维账号。

建议白名单优先使用以下方式之一：

- 用户 ID
- 数据库字段 `is_super_admin`
- 独立的系统账号标记

不建议长期依赖用户名字符串，因为用户名可能变更或复用。

---

## 7. 权限更新策略

权限配置变化时，应主动刷新缓存。

### 7.1 需要刷新缓存的场景

- 新增 permission
- 更新 permission
- 删除 permission
- 更新 role_permission 关系
- 更新 user_role 关系
- 调整接口权限绑定

### 7.2 刷新范围

应至少刷新：

- 受影响用户的角色缓存
- 受影响用户的权限缓存
- 受影响接口的权限映射缓存

---

## 8. 推荐的数据约束

为了降低脏数据风险，建议后续在数据层补充：

1. `permission.code` 唯一
2. `role.role_code` 唯一
3. `role_permission(role_id, permission_id)` 唯一
4. `user_role(user_id, role_id)` 唯一
5. 禁用权限不能继续用于新授权
6. 系统角色不可删除

---

## 9. 风险与注意事项

### 9.1 不建议默认放行未配置权限的接口

如果接口在数据库中没有找到映射，默认放行会有安全风险。

更稳妥的策略是：

- 开发阶段可以临时放行并打日志
- 生产阶段建议默认拒绝，要求显式配置权限

### 9.2 路由匹配要规范化

不要直接用原始 URL 作为唯一键，因为会遇到：

- 路径参数问题
- Query 参数问题
- 尾部斜杠问题
- 同一路径不同方法问题

建议使用：

- `method + normalized_path`

### 9.3 数据权限和功能权限要区分

RBAC 解决的是“能不能访问某个功能接口”。

例如：

- 能否查看“我的申请”
- 能否审核申请
- 能否查看所有学生

其中“能否看自己的数据”仍属于数据权限范畴，不能只靠 RBAC 完全解决。

---

## 10. 建议的落地顺序

1. 先定义权限码规范
2. 再定义接口与权限的映射规则
3. 再实现 Redis 缓存结构
4. 再实现白名单和公开接口
5. 再实现 `PermissionMiddleware`
6. 再补充权限变更时的缓存刷新
7. 最后补齐前端菜单和按钮权限展示

---

## 11. 文档结论

这套方案总体是可行的，适合你的保研加分平台。

它的优点是：

- 模型清晰
- 性能可控
- 易于扩展
- 适合后台系统

但要特别注意：

- 不要把“未配置权限”简单当成“公开接口”
- 白名单不要过大
- 接口权限缓存要和权限变更同步刷新
- 数据权限需要单独设计
