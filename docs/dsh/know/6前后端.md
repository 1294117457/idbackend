## 完整架构

```
┌─────────────────────────────────┐          ┌──────────────────────────────────┐
│  Host（Node.js 进程）            │          │  Client（浏览器）                  │
│                                 │          │                                  │
│  ctx (Host)                     │          │  ctx (Client)                    │
│  ├── ctx.tools   ← 工具注册     │          │  ├── ctx.slots  ← UI 注册        │
│  ├── ctx.llm     ← 模型调用     │   HTTP   │  ├── ctx.theme  ← 主题           │
│  ├── ctx.sessions ← 会话管理   ─┼──────────┼─►  ctx.sessions (镜像)           │
│  ├── ctx.fs      ← 文件操作     │   SSE    │  ├── ctx.connection ← 通信管道   │
│  ├── ctx.shell   ← 命令执行     │◄─────────┼── ctx.remote   ← RPC 调用       │
│  └── ctx.settings ← 设置持久化  │          │  └── ctx.locale ← 国际化         │
│                                 │          │                                  │
└─────────────────────────────────┘          └──────────────────────────────────┘
         后端逻辑直接绑 ctx                          前端 UI 通过 slot 组合
```



## 前后端怎么连接？

通过 `packages/client/connection/` 和 `packages/host/webserver/` 这一对：

| 方向        | 通道                                | 例子                                             |
| :---------- | :---------------------------------- | :----------------------------------------------- |
| 前端 → 后端 | HTTP API（RPC 调用）                | 用户输入消息 → `POST /api/sessions/:id/messages` |
| 后端 → 前端 | SSE（Server-Sent Events，实时推送） | AI 生成 token → 实时流到浏览器显示               |

------

## 具体流程举例：用户发送一条消息

```
1. 用户在浏览器输入框打字，按回车
   │
   ▼  Client ctx
2. ui-conversation 的 InputBar 组件触发提交
   │
   ▼
3. ctx.connection.api.sendMessage(sessionId, text)
   │  （HTTP POST 到后端）
   │
   ═══════════════ 网络 ═══════════════
   │
   ▼  Host ctx
4. Host 收到请求 → ctx.sessions 写入消息 → 触发 Agent 循环
   │
   ▼
5. ctx.agentLoop 启动 turn → ctx.llm.stream() 调模型
   │
   ▼
6. 模型返回 token → ctx.sessions.append('assistant/chunk', ...)
   │
   ▼
7. session/event 事件通过 SSE 推送到前端
   │
   ═══════════════ 网络 ═══════════════
   │
   ▼  Client ctx
8. ctx.connection 收到 SSE → 更新 Client 的 session 状态
   │
   ▼
9. ui-conversation 的 ChatView 检测到数据变化 → 实时渲染气泡
```

## 你的理解修正版

| 你的说法                    | 修正                                          |
| :-------------------------- | :-------------------------------------------- |
| "核心总线是 ctx"            | ✓ 但是有两个 ctx——Host 一个，Client 一个      |
| "前端 UI 基于 slot 连接"    | ✓ 前端内部的组件通过 slot 组合                |
| "后端逻辑直接绑定到 ctx 上" | ✓ 后端的工具、模型、文件系统都注册在 Host ctx |
| （缺失）前后端之间          | 通过 HTTP/SSE 桥接，不是共享 ctx              |

## 一句话

后端是一棵 Cordis 插件树，前端是另一棵 Cordis 插件树，中间靠 HTTP/SSE 通信。 两棵树各自用 `ctx` 管理自己内部的组件/服务，但彼此不共享 `ctx`。

```
这里的后端不是传统web后端那样，比如前端操作，发送请求，后端接收请求，在业务层处理并且间距传递到持久层对吗
这里是前端操作，然后rpc调用后端接口，然后实时处理前端操作，比如接收前端传递的用户数据，拼接上下文，和模型对话
```

```
Host ctx 上有：        Client ctx 上有：
ctx.tools              ctx.slots
ctx.llm                ctx.theme
ctx.fs                 ctx.locale
ctx.shell              ctx.connection
ctx.sessions           ctx.sessions（镜像）
ctx.settings           ctx.settingsScope
```

```
也就是说，
	比如传统前端是路由层自上而下的获取路由、组件+请求，
	后端也是接口、业务、持久层和相关中间件绑定，耦合度高
	
	操作传统前端一个模块，要到对应路由、请求同样修改，操作一个传统后端要接口、业务、持久层和中间件全链路修改

crodis范式，
	前后端都是是配置文件中自由注册组件，然后组件基于配置文件自下而上嵌入ctx对吗
	crodis接入就是准备好插件，然后在配置文件配置，然后将插件基于ctx插入对应位置对吗，

```
