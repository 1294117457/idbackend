# 保研系统四层职责链设计

## 设计原则

**Template 系统只做一件事：基于证明材料计算加分。**

四六级成绩、游泳等级等资质信息不属于加分计算范畴，由管理员直接录入 `user.extra_info`，不走申请审批流程。

---

## 一、总览

```
TemplateCategory  →  Template  →  Application  →  ScoreData
（分类树 + 上限）    （计分规则）    （申请流水）       （通过的流水）
                                                        ↓
                                               User.score_info（汇总快照）
```

---

## 二、数据对象设计

### 1. TemplateCategory（分类树）

职责：定义分类层级和各级分值上限，纯配置数据。`is_bind_template` 字段**唯一作用**是标识"该节点已绑定 Template"，与子分类/性能优化无关。

```sql
CREATE TABLE template_category (
    id          SERIAL PRIMARY KEY,
    name        VARCHAR(100) NOT NULL,
    parent_id   INTEGER REFERENCES template_category(id),
    max_score   DECIMAL(5,2) NOT NULL CHECK (max_score >= 0),  -- 不允许 null（每级必须有上限）
    is_bind_template BOOLEAN DEFAULT FALSE, -- TRUE=已绑 template；FALSE=未绑 template（可绑可加子）
    sort_order      INTEGER DEFAULT 0,   -- 由管理员手动指定，未指定的视为 0，列表展示时排同级末尾
    is_active   BOOLEAN DEFAULT TRUE,
    description VARCHAR(255),
    created_at  TIMESTAMP,
    updated_at  TIMESTAMP
);
```

**示例数据：**

```
id | name     | parent_id | max_score | is_bind_template | sort_order
 1 | 加分总计  | null      | 100.00    | FALSE   | 1
 2 | 学业加分  | 1         | 60.00     | FALSE   | 1
 3 | 专长加分  | 1         | 20.00     | TRUE    | 2       ← 可绑 template（可绑多个）
 4 | 劳动教育  | 1         | 20.00     | TRUE    | 3       ← 可绑 template（可绑多个）
 5 | 竞赛奖项  | 2         | 20.00     | TRUE    | 1       ← 可绑 template（可绑多个）
 6 | 学术论文  | 2         | 10.00     | TRUE    | 2       ← 可绑 template（可绑多个）
```

> 同级展示顺序：`ORDER BY sort_order ASC, id ASC`（sort_order=0 视为排在同级末尾但 id 升序保稳定）。

**is_bind_template 状态机（v2，仅服务于"能否绑 template + 能否加子"）：**

```
is_bind_template=FALSE  → 未绑 template（可绑 template，可加子分类）
is_bind_template=TRUE   → 已绑 template（不可绑更多，不可加子）
```

`is_bind_template` 仅表示"是否已绑 template"，与子分类数量、template 数量、性能优化都无关：

- 创建分类时：新节点默认 `is_bind_template=FALSE`
- 绑定 template 时：由 `TemplateService.create` 显式调用 `bind_template()` 翻为 TRUE
- 添加子分类时：校验父节点 `is_bind_template=FALSE`（未绑 template），无父子数量限制
- 删除 template 时：由 `TemplateService.delete` 检查剩余数量归零后调 `unbind_template()` 翻回 FALSE
- 删除分类时：级联删除所有子分类与绑定的 template（DB CASCADE）；无需回滚父 flag

**校验规则：**

- 绑定 template 时：分类 `is_bind_template=FALSE` 才能绑；绑后翻 TRUE
- 添加子分类时：父节点必须 `is_bind_template=FALSE`，无父子数量限制
- 删除分类时：**级联删除所有子分类与绑定的 template**（前端管理界面在删除前做强提醒，确认后执行）
- `max_score` NOT NULL 且 `>= 0`（DB 层 CHECK）
- **不校验**子分类 `max_score` 之和与父 `max_score` 的关系——子分类分数之和由 `recalculate` 步骤的 `min(∑, 父 max_score)` 自然封顶
- **不提供**修改父节点（move / change_parent）能力，要调整位置只能"删除旧节点 + 新建子节点"

**删除的级联策略（DB 层）：**

```sql
-- template.category_id 改为 ON DELETE CASCADE：分类被删时 template 一起删
ALTER TABLE template
    DROP CONSTRAINT fk_template_category_old,
    ADD CONSTRAINT fk_template_category
        FOREIGN KEY (category_id) REFERENCES template_category(id)
        ON DELETE CASCADE;
```

template 被级联删除后，下挂的 rule / template_rule / rule_attribute 不受影响（template 不引用 attribute，rule / attribute 是独立的可复用字典数据）。

> application 历史不受影响：application 通过 `template_id` 外键引用 template，template 被级联删除时若 application 存在，会失败——这种情况由 service 层在删除前预检"该分类下是否有未关闭的 application"，若有则禁止删除（保守策略，避免历史被误删）。

**is_active 软启用：**

- `is_active=FALSE` 的分类在 `get_tree` 中不返回（管理端看不到、学生端选择不到）
- 不影响历史 application：application 在生成时已快照 `template_name/template_id/category_id` 等字段，score_data 与 application 的关联不受分类失效影响
- 失效分类下的历史 score_data 仍参与 `recalculate` 聚合（按历史快照 category_id 归类），只有该分类被硬删除才会清理

### 2. Template（计分模板）

职责：定义具体的计分逻辑，聚合 Rule 和 Attribute，是计算引擎的入口。

共 5 张表，结构参考 RBAC 的 user → role → permission 三层解耦方式：

```
template ──< template_rule >── rule ──< rule_attribute >── attribute
```

一个 template 可以绑定**多个** rule（多选/多填场景），本设计**不在 service 层校验** rule 之间的冲突（例如互斥/必填），由后台管理员配置时自行注意。

---

#### 表1：template（聚合根）

```sql
CREATE TABLE template (
    id            SERIAL PRIMARY KEY,
    name          VARCHAR(100) NOT NULL,
    category_id   INTEGER NOT NULL REFERENCES template_category(id) ON DELETE CASCADE,  -- 只绑叶子节点，分类被删时级联删除 template
    max_score     DECIMAL(5,2) NOT NULL,   -- 本模板单次申请上限（独立封顶，与所属分类 max_score 无关）
    sort_order    INTEGER DEFAULT 0,
    description   TEXT,
    review_count  INTEGER DEFAULT 1,
    is_active     BOOLEAN DEFAULT TRUE,
    created_at    TIMESTAMP,
    updated_at    TIMESTAMP
);
```

---

#### 表2：rule（选项组，可复用）

一个 rule = 前端一个选择组（下拉框）或输入组。rule 独立存在，可被多个 template 复用。

```sql
CREATE TABLE rule (
    id          SERIAL PRIMARY KEY,
    name        VARCHAR(100) NOT NULL,
    description TEXT,
    created_at  TIMESTAMP,
    updated_at  TIMESTAMP
);
```

> 注意：本设计目前**未给 rule 设置 `is_required` 字段**。`ScoreCalculationService.calculate()` 对未选 rule 采取 `skip`（不参与计分）的策略。如未来需要必填语义，在 rule 表新增 `is_required BOOLEAN DEFAULT FALSE` 并在 calculate 与提交校验中加判断。

---

#### 表3：attribute（计算属性，可复用）

一个 attribute = 下拉框中的一个选项，或一段区间公式。attribute 独立存在，可被多个 rule 复用。

**类型由 `attribute_type` 显式声明：**

- `CONDITION`：value 为数字字符串（如 `"10"`），用户选中该选项后直接得该分数
- `TRANSFORM`：value 为公式字符串（如 `"input * 0.5"`），用户输入数值后套公式计算，配合 `input_min`/`input_max` 限定区间（**半开半闭**：`input_min <= input < input_max`）

```sql
CREATE TABLE attribute (
    id              SERIAL PRIMARY KEY,
    name            VARCHAR(100) NOT NULL,  -- 选项显示名，如"国家级"、"0-60学分"
    attribute_type  VARCHAR(20)  NOT NULL
                    CHECK (attribute_type IN ('CONDITION', 'TRANSFORM')),
    value           TEXT NOT NULL,          -- CONDITION: 数字字符串；TRANSFORM: 公式（含 input）
    input_min       DECIMAL(10,4),          -- TRANSFORM 区间下限（null = 无限制；匹配语义 >=）
    input_max       DECIMAL(10,4),          -- TRANSFORM 区间上限（null = 无限制；匹配语义 <）
    sort_order      INTEGER DEFAULT 0,      -- 全局唯一排序依据，任何 rule 中都按此排序
    description     TEXT,                   -- 公式说明等备注
    is_active       BOOLEAN DEFAULT TRUE,
    created_at      TIMESTAMP,
    updated_at      TIMESTAMP
);
```

**attribute 校验（在 service 层 `AttributeService.validate()`）：**

- `CONDITION`：`value` 必须匹配非负数字（正则 `^[0-9]+(\.[0-9]+)?$`）
- `TRANSFORM`：`value` 必须只包含 `0-9 + - * / ** ( ) .` 和变量名 `input`（禁止函数调用、禁止内置名如 `sum/max/min`）
- `input_min`/`input_max`：允许 null；非 null 时 `input_min >= 0`；当两者都非 null 时 `input_min < input_max`

**attribute 删除行为：**

attribute 的修改/删除**不影响**已有 application（application 只通过 `template.apply_score` 引用 template，与 attribute 无直接外键关联）。删除 attribute 时直接删除，**无 DB 级 ON DELETE 限制**；如果该 attribute 还被某条 `rule_attribute` 引用，由 service 层在删除前清理该关联（`rule_attribute.attribute_id` 级联删除，但 application 历史不受影响）。

---

#### 表4：template_rule（template-rule 多对多）

```sql
CREATE TABLE template_rule (
    id          SERIAL PRIMARY KEY,
    template_id INTEGER NOT NULL REFERENCES template(id) ON DELETE CASCADE,
    rule_id     INTEGER NOT NULL REFERENCES rule(id),
    sort_order  INTEGER DEFAULT 0,         -- rule 在该 template 中的显示顺序
    UNIQUE (template_id, rule_id)
);

CREATE INDEX idx_template_rule_template ON template_rule(template_id);
```

---

#### 表5：rule_attribute（rule-attribute 多对多）

```sql
CREATE TABLE rule_attribute (
    id           SERIAL PRIMARY KEY,
    rule_id      INTEGER NOT NULL REFERENCES rule(id) ON DELETE CASCADE,
    attribute_id INTEGER NOT NULL REFERENCES attribute(id) ON DELETE CASCADE,
    -- 排序统一使用 attribute.sort_order，同一 attribute 在所有 rule 中顺序一致
    UNIQUE (rule_id, attribute_id)
);

CREATE INDEX idx_rule_attribute_rule ON rule_attribute(rule_id);
```

---

**示例一：条件选择（竞赛奖项）**

```
template(name="竞赛奖项", category_id=学业加分, max_score=10)
  └── rule(name="奖项等级")          ← 前端下拉框，用户选一项
        ├── attribute(type=CONDITION, name="国家级", value="10")   ← 选中得10分
        ├── attribute(type=CONDITION, name="省级",   value="5")    ← 选中得5分
        └── attribute(type=CONDITION, name="院级",   value="2")    ← 选中得2分
```

**示例二：区间公式（劳动学分换算）**

注意：本设计区间为**半开半闭**：`input_min <= input < input_max`。所以 "0-60 学分" 应配置为 `input_min=0, input_max=61`；"61-100 学分" 应配置为 `input_min=61, input_max=101`（或留 `input_max=null`）。

```
template(name="劳动学分换算", category_id=劳动教育, max_score=10)
  └── rule(name="学分区间")          ← 前端输入框，系统按 input_min/max 自动匹配
        ├── attribute(type=TRANSFORM, name="0-60学分",   value="input * 0.5",           input_min=0,   input_max=61)
        └── attribute(type=TRANSFORM, name="61-100学分", value="30 + (input-60) * 0.3", input_min=61,  input_max=null)
```

**示例三：无范围公式（直接换算）**

```
template(name="GPA换算", category_id=学业加分, max_score=20)
  └── rule(name="GPA")              ← 前端输入框，只有1条公式，直接套用
        └── attribute(type=TRANSFORM, name="GPA换算", value="input * 5", input_min=null, input_max=null)
```

### 3. Application（申请记录）

职责：记录学生的一次加分申请，包含快照数据、审批状态和操作日志。

共 3 张表：

---

#### applications（申请主表）

```sql
CREATE TABLE score_applications (
    id             SERIAL PRIMARY KEY,
    user_id        INTEGER NOT NULL REFERENCES users(id),
    template_id    INTEGER NOT NULL REFERENCES template(id),
    template_name  VARCHAR(100) NOT NULL,   -- 快照，防模板改名影响历史
    category_id    INTEGER NOT NULL REFERENCES template_category(id),  -- 冗余，便于聚合
    apply_score    DECIMAL(5,2) NOT NULL,   -- 由 template 计算得出，提交时一次性快照，后续不可改
    gain_score     DECIMAL(5,2) DEFAULT 0,  -- 已通过 proof 的 proof_score 之和（SQL 原子更新）
    status         VARCHAR(20) DEFAULT 'DRAFT'
                   CHECK (status IN ('DRAFT','APPLYING','PASSED','REJECTED')),
    review_count   INTEGER DEFAULT 1,       -- 从 template.review_count 快照，需几人审核
    approved_count INTEGER DEFAULT 0,       -- 已投赞成票的审核员数（SQL 原子 +1）
    created_at     TIMESTAMP,
    updated_at     TIMESTAMP
);

CREATE INDEX idx_application_user   ON score_applications(user_id);
CREATE INDEX idx_application_status ON score_applications(status);
```

**status 流转：**

```
DRAFT ──SUBMIT──> APPLYING ──PASS──> PASSED（终态，写 ScoreData）
                          └──REJECT─> REJECTED ──RESUBMIT──> APPLYING
```

各状态说明：

- `DRAFT`：草稿，学生保存未提交，可编辑
- `APPLYING`：已提交，审核中，锁定不可修改（学生侧只能走 RESUBMIT）
- `PASSED`：审核员投票达到 `review_count`，触发 ScoreData 写入（终态，锁定）
- `REJECTED`：审核员整体拒绝，学生可修改 proof 后重新提交

> 本设计**不引入 REVOKED 状态**。已通过的申请如果要撤销，由专门的"撤销流程"（未来扩展）在 score_data 层面处理，不回改 application.status。

**关键规则：**

- `apply_score` 由计算引擎在 `save_draft` 时一次性算出并固化到 application；**后续 RESUBMIT 不允许修改 apply_score**，只能修改 proof。要改分数必须重新生成申请。
- 提交时（SUBMIT 与 RESUBMIT）校验：**所有 proof 的 `proof_score` 之和必须严格等于 `apply_score`**
- 审核员标记 PASS 前置条件：**该 application 下所有 proof 均为 `APPROVED` 状态**（不依赖 gain_score 反推）
- `approved_count >= review_count` → 自动将 status → PASSED（SQL 原子更新，同一事务内写 ScoreData）
- 任意审核员点 REJECT（必须带 remark 评价）→ status 立即变为 REJECTED

---

#### application_proofs（证明材料）

```sql
CREATE TABLE application_proofs (
    id             SERIAL PRIMARY KEY,
    application_id INTEGER NOT NULL REFERENCES score_applications(id) ON DELETE CASCADE,
    file_id        INTEGER NOT NULL REFERENCES file_metadata(id),
    proof_score    DECIMAL(5,2) NOT NULL,   -- 学生填写；sum 必须严格等于 application.apply_score
    status         VARCHAR(20) DEFAULT 'PENDING'
                   CHECK (status IN ('PENDING','APPROVED','REJECTED')),
    created_at     TIMESTAMP,
    updated_at     TIMESTAMP
);

CREATE INDEX idx_proofs_application ON application_proofs(application_id);
```

**关键约束：**

- proof 数量由学生自由决定（>= 1）
- 任何允许写 proof 的入口（save_draft / submit / resubmit）都必须校验：当前 application 下**所有 proof 的 `proof_score` 之和 == `application.apply_score`**
- proof_score 为非负 DECIMAL

**proof 审批逻辑：**

- 审核员逐条标记 proof APPROVED/REJECTED
- proof APPROVED → `application.gain_score += proof.proof_score`（同一事务，SQL 原子更新）
- 当 application 下**所有 proof.status == APPROVED** 时 → 审核员方可点击 application 整体 PASS

**REJECTED 后修改规则：**

- 学生可在 RESUBMIT 时**删除 REJECTED 的 proof 并重新上传**（新 proof 状态为 PENDING）
- APPROVED 的 proof 不可被学生操作；APPROVED 的 proof_score 已累加进 `gain_score`，**不回退**
- 重新提交（RESUBMIT）后 `application.status → APPLYING`，APPROVED proof 保持已通过状态；之前尚未审核的 proof 仍是 PENDING
- RESUBMIT 时必须重新校验 `sum(proof_score) == apply_score`（因为 proof 集合可能变了）

---

#### application_operation（操作日志）

职责：追加只写的审计日志，记录申请的所有操作。草稿保存不记录日志。

```sql
CREATE TABLE application_operation (
    id               SERIAL PRIMARY KEY,
    application_id   INTEGER NOT NULL REFERENCES score_applications(id),
    operator_id      INTEGER NOT NULL,
    operator_name    VARCHAR(100) NOT NULL,  -- 快照操作人姓名（审核员可能离职）
    operation        VARCHAR(30)  NOT NULL
                     CHECK (operation IN ('SUBMIT','REVIEW_PROOF','PASS','REJECT','RESUBMIT')),
    target_id        INTEGER,                 -- 关联对象 id（proof_id 或 application_id，NULL 表示无关联）
    target_type      VARCHAR(20),             -- 'PROOF' 或 'APPLICATION'，NULL 表示无关联
    remark           TEXT,                    -- REJECT 时必填，其他可选
    created_at       TIMESTAMP DEFAULT NOW()  -- 无 updated_at，操作记录不可修改
);

CREATE INDEX idx_operation_application ON application_operation(application_id);
CREATE INDEX idx_operation_target      ON application_operation(target_id, target_type);
```

**操作说明：**

- `SUBMIT`：学生提交申请（DRAFT → APPLYING）
- `REVIEW_PROOF`：审核员对单条 proof 做出决定（APPROVED/REJECTED），`target_id=proof_id, target_type='PROOF'`
- `PASS`：审核员标记申请整体通过（approved_count 累加，达到 review_count 时 → PASSED），`target_id=application_id, target_type='APPLICATION'`
- `REJECT`：审核员拒绝整体申请（→ REJECTED），**remark 必填**，`target_id=application_id, target_type='APPLICATION'`
- `RESUBMIT`：学生修改后重新提交（REJECTED → APPLYING）

**操作日志示例：**

```
operator    | operation    | target_type | target_id | remark
张三(学生)  | SUBMIT       | NULL        | NULL      | NULL
李老师      | REVIEW_PROOF | PROOF       | 456       | "第4个材料格式不符"
李老师      | PASS         | APPLICATION | 101       | "其余材料均符合要求"
王老师      | PASS         | APPLICATION | 101       | NULL       ← approved_count=2=review_count → PASSED
李老师      | REJECT       | APPLICATION | 102       | "国家级证书编号无法在系统中检索"
张三(学生)  | RESUBMIT     | NULL        | NULL      | NULL
```

---

**关键设计：**

- `apply_score` 由计算引擎在 save_draft 时算出并快照，**学生不可填写，RESUBMIT 不可修改**
- `gain_score` / `approved_count` 用 SQL 算术表达式原子更新，禁止 ORM 读-改-写
- `template_name` / `review_count` / `operator_name` 均为快照，防止源数据变更影响历史
- DRAFT 状态不记录 operation，提交（SUBMIT）时才开始记录
- 操作日志的 `target_id`/`target_type` 字段使 proof 级与 application 级审计均可索引

### 4. ScoreData（流水记录）

职责：记录每条申请通过（`application.status → PASSED`）后的得分，作为聚合计算的原始数据，追加只写。

```sql
CREATE TABLE score_data (
    id             SERIAL PRIMARY KEY,
    user_id        INTEGER NOT NULL REFERENCES users(id),
    application_id INTEGER NOT NULL REFERENCES score_applications(id),
    category_id    INTEGER NOT NULL REFERENCES template_category(id),  -- 叶子节点
    name           VARCHAR(100),            -- 模板名快照，展示用
    score          DECIMAL(5,2) NOT NULL,   -- application.gain_score 快照
    is_active      BOOLEAN DEFAULT TRUE,    -- FALSE = 该申请被外部标记为失效，recalculate 时排除
    created_at     TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_score_data_user_active ON score_data(user_id, is_active);
```

**写入时机：** `application.status → PASSED` 时由 `ApplicationService.pass_application()` 在同一事务内调用 `ScoreDataService.record()` 写入一条（approved_count 达到 review_count 时触发）。

**失效处理（is_active=FALSE）：** 未来如果增加"撤销已通过申请"的扩展能力，将对应 `score_data.is_active = FALSE`，下次 `recalculate` 自动排除，`user.score_info` 自然更新。本期**不实现该流程**。

**聚合算法（自底向上树遍历）：**

```
Step 1：SQL 聚合叶子分类原始分
  SELECT category_id, SUM(score)
  FROM score_data
  WHERE user_id = ? AND is_active = TRUE
  GROUP BY category_id

Step 2：内存中组装 template_category 树（一次全表查询，按 parent_id 建树）

Step 3：后序递归，自底向上封顶
  叶子节点：capped = min(SUM(score), category.max_score)
  非叶节点：capped = min(sum(子节点 capped), category.max_score)

Step 4：覆盖写入 user.score_info（幂等，可反复触发）
```

> template.max_score 已在 calculate 阶段完成独立封顶（写入 score_data 的 score 已经 ≤ template.max_score），此处分类封顶是上一层级的自然封顶。

**算法示例（4 层树）：**

```
总分(max=100)
  └── 加分(max=80)
        ├── 学业(max=60)：竞赛raw=25→capped=20，论文raw=15→capped=10，学业capped=min(30,60)=30
        └── 专长(max=30)：体育raw=35→capped=30，专长capped=min(30,30)=30
加分capped = min(30+30, 80) = 60
总分capped = min(60, 100) = 60
```

```python
# 计算引擎（calculation_service.py）
# 依赖：pip install simpleeval（安全的数学公式解析，禁止任意代码执行）
from simpleeval import simple_eval

class ScoreCalculationService:

    @staticmethod
    def calculate(template, user_selections: dict) -> float:
        """
        遍历 template 的所有 rule，按 template_rule.sort_order 顺序处理：
        user_selections 结构：
          { rule_id: attribute_id }     # CONDITION 规则：用户选中的 attribute id
          { rule_id: "75.0" }           # TRANSFORM 规则：用户输入的数值字符串
        返回封顶后的分数（min(total, template.max_score)）。
        """
        total = 0.0
        for template_rule in sorted(template.template_rules, key=lambda tr: tr.sort_order):
            rule = template_rule.rule
            selected = user_selections.get(rule.id)
            if selected is None:
                continue  # 未填写的 rule 不参与计分

            # rule 内的 attribute 排序统一按 attribute.sort_order
            for attr in sorted(rule.attributes, key=lambda a: a.sort_order):
                if attr.attribute_type == 'CONDITION':
                    if selected == attr.id:
                        total += float(attr.value)
                        break

                elif attr.attribute_type == 'TRANSFORM':
                    user_input = float(selected)
                    # 半开半闭区间匹配：input_min <= input < input_max
                    if attr.input_min is not None and user_input < float(attr.input_min):
                        continue
                    if attr.input_max is not None and user_input >= float(attr.input_max):
                        continue
                    # 使用 simpleeval 替代 eval，禁止任意代码执行
                    total += simple_eval(attr.value, names={"input": user_input})
                    break

        return min(total, float(template.max_score))
```

### Layer 3：ApplicationService

```python
class ApplicationService:

    @staticmethod
    async def save_draft(db, user_id, template_id, user_selections, proof_data_list) -> Application:
        """
        保存草稿（DRAFT），不写 application_operation：
        1. 调用 ScoreCalculationService.calculate() 算出 apply_score
        2. 校验 sum(proof.proof_score) == apply_score（数量学生自定，总分必须严格相等）
        3. 创建/更新 Application（status=DRAFT，apply_score 快照）和 ApplicationProof 列表
        """

    @staticmethod
    async def submit(db, application_id, user_id) -> Application:
        """
        前置条件：application.status IN ('DRAFT', 'REJECTED')
        提交申请（DRAFT/REJECTED → APPLYING）：
        - 重新校验 sum(proof.proof_score) == apply_score
        - application.status → APPLYING
        - 写 application_operation（operation=SUBMIT）
        """

    @staticmethod
    async def review_proof(db, proof_id, reviewer_id,
                           action: str, remark: str) -> None:
        """
        前置条件：application.status == 'APPLYING'
        审核员对单条 proof 做出决定（同一事务）：
        action = 'APPROVED' 或 'REJECTED'
        - APPROVED：UPDATE proof SET status='APPROVED'
                    UPDATE application SET gain_score = gain_score + proof.proof_score（SQL 原子）
        - REJECTED：UPDATE proof SET status='REJECTED'
        写 application_operation（operation=REVIEW_PROOF, target_id=proof_id, target_type='PROOF',
                              remark 说明原因）
        """

    @staticmethod
    async def pass_application(db, application_id, reviewer_id, remark) -> Application:
        """
        前置条件：
          1. application.status == 'APPLYING'
          2. 该 application 下所有 proof.status == 'APPROVED'（proof 全过才能 pass）
        审核员投票通过（同一事务）：
        - UPDATE application SET approved_count = approved_count + 1（SQL 原子）
        - 若 approved_count >= review_count → application.status → PASSED
                                              ScoreDataService.record() 写流水
        - 写 application_operation（operation=PASS, target_id=application_id, target_type='APPLICATION'）
        """

    @staticmethod
    async def reject_application(db, application_id, reviewer_id, remark: str) -> Application:
        """
        前置条件：application.status == 'APPLYING'
        审核员整体拒绝：
        - application.status → REJECTED
        - 写 application_operation（operation=REJECT, target_id=application_id, target_type='APPLICATION',
                                remark=必填）
        - remark 必须在 service 层校验非空
        """

    @staticmethod
    async def resubmit(db, application_id, user_id,
                       delete_proof_ids, new_proof_data_list,
                       remark) -> Application:
        """
        前置条件：application.status == 'REJECTED'
        学生修改 proof 后重新提交（同一事务）：
        1. 校验 delete_proof_ids 中每条 proof.status == 'REJECTED'（APPROVED 的不可动）
        2. 校验修改后的 proof 集合仍满足 sum(proof.proof_score) == apply_score
           （apply_score 不可改，proof 必须凑够/凑少到与原 apply_score 严格相等）
        3. 删除指定 proof，INSERT 新 proof（status=PENDING）
           - 已 APPROVED 的 proof 保持原状，其 gain_score 贡献已计入，不回退
        4. application.status → APPLYING
        5. 写 application_operation（operation=RESUBMIT）

        注：如要修改 apply_score，必须重新生成新申请（save_draft 新 application）。
        """
```

## 四、完整业务流程

```
管理端配置（一次性）
  1. 配置 TemplateCategory 分类树（加分总计 → 学业/专长/劳动）
  2. 在叶子分类下创建 Template，可挂多个 Template（每个 template 独立按其 max_score 封顶，不相互影响；分类层级封顶由 recalculate 处理）
  3. 在 Template 下挂多个 Rule 与 Attribute（业务自行保证 rule 不冲突）

学生申请
  4. 前端加载 TemplateCategory 树，选择叶子分类
  5. 选择 Template，加载规则数据 → 前端本地实时计算分数（无需后端 preview 接口）
  6. 填写 proof 材料及分值（数量自定，sum 必须 == apply_score，前后端均校验）
  7. 保存草稿 → ApplicationService.save_draft()
       └── 算 apply_score（快照固化），校验 sum(proof_score) == apply_score
       └── 不记录 operation
  8. 确认提交 → ApplicationService.submit()
       └── 重新校验 sum == apply_score
       └── application.status → APPLYING，写 SUBMIT 操作日志

审批
  9.  审核员逐条审核 Proof → ApplicationService.review_proof()
       └── proof.status → APPROVED/REJECTED
       └── APPROVED 时 gain_score 原子累加，写 REVIEW_PROOF 操作日志
  10. 该申请下所有 proof 均为 APPROVED 时，审核员可投票通过
       → ApplicationService.pass_application()
       └── approved_count 原子 +1
       └── approved_count >= review_count → status → PASSED，ScoreDataService.record() 写流水
     或 审核员拒绝（必须带 remark 评价）→ ApplicationService.reject_application()
       └── status → REJECTED，写 REJECT 操作日志（remark 必填）

再提交
  11. 学生修改被驳回的 proof → ApplicationService.resubmit()
       └── 只允许删除 REJECTED proof、上传新 proof（APPROVED 不可动）
       └── sum(proof_score) 仍必须 == apply_score（apply_score 不可改）
       └── status → APPLYING，写 RESUBMIT 操作日志
       └── 如需改分数，重新生成新申请（new save_draft）

成绩汇总
  12. 管理员触发 ScoreDataService.recalculate()
       └── 按分类聚合 → 逐层封顶 → 覆盖写入 user.score_info
  13. 前端展示 → ScoreDataService.get_summary() 读 score_info
```
