## 按年区分，更好的做法是路径前缀

```
idpython-bucket/
├── 2025/
│   ├── proofs/{application_id}/{uuid}.pdf
│   └── policies/{uuid}_文件名.pdf
└── 2026/
​    ├── proofs/{application_id}/{uuid}.pdf
​    └── policies/{uuid}_文件名.pdf
```



### 你的三类文件，本质区别是访问控制

| 文件类型          | 谁能访问          | 访问方式               |
| :---------------- | :---------------- | :--------------------- |
| 头像              | 所有登录用户可看  | 可以公开或短期链接     |
| 申请材料（proof） | 仅上传人 + 审核员 | 必须鉴权，用预签名 URL |
| 政策文件          | 所有学生可下载    | 可以公开读             |

------

### 推荐方案：单 Bucket + 路径前缀区分

对于你这个规模的系统，不需要多 bucket，用一个 bucket + 有意义的 key 前缀即可：

```
idpython-bucket/
├── avatars/
│   └── {user_id}/{uuid}.jpg          # 头像
├── proofs/
│   └── {application_id}/{uuid}.pdf   # 申请材料
└── policies/
​    └── {uuid}_{原始文件名}.pdf        # 政策文件
```

为什么当前代码不够好：

你现在的代码（`file_service.py` 第 30 行）生成的 `object_name` 是：

object_name = f"{uuid.uuid4()}.{ext}"  *# 如：abc123.pdf*

没有任何路径前缀，所有文件平铺在 bucket 根目录，无法区分类型，也没法做批量清理。

------

### 三类文件分别怎么处理

#### 1. 头像（AVATAR）

- 特点：频繁展示，文件小（图片），可以公开
- Key 格式：`avatars/{user_id}/{uuid}.jpg`
- 访问方式：生成预签名 URL，有效期设 7 天（头像不需要短期）
- 注意：用户重新上传头像时，旧头像应该物理删除，避免存储浪费

#### 2. 申请材料（PROOF）

- 特点：隐私数据，只有本人和审核员能看，需要严格鉴权
- Key 格式：`proofs/{application_id}/{uuid}.{ext}`
- 访问方式：每次访问都通过后端鉴权，然后生成短期预签名 URL（1小时）
- 注意：前端不能直接拿到永久链接，每次预览都要走 `/api/file/{id}/preview` 接口

流程：前端请求预览 → 后端验证用户有权限看这个申请 → 生成1小时预签名URL → 返回给前端

#### 3. 政策文件（POLICY）

- 特点：公开内容，所有学生可下载，管理员上传
- Key 格式：`policies/{uuid}_{原始文件名}`（保留原始名方便辨识）
- 访问方式：这里有两种选择：
  - 方案A：也用预签名 URL（统一管理，推荐）
  - 方案B：设置 bucket/prefix 为公开读，直接返回静态 URL（更简单，但权限控制弱）

你现有的 `policy_documents` 表是用于 RAG（AI问答）的，把文档内容存数据库做 embedding。这和"学生可以下载政策文件"是两件事——下载走 SeaweedFS，RAG 走数据库文本。
