## 1. 设计原则

1. **Service 极度精简且完整**：只做"接请求 → 调存储 → 调 DB → 构造返回对象"四件事。数据转换（ORM→VO、分页封装）全部在 service 层完成，路由层只做参数收集和透传，不碰任何数据。
2. **DTO 承担转换和数据校验**：Request 校验输入并提供转换方法——
   - `to_metadata(user_id)`：构造 ORM 对象（新增/创建场景）
   - `apply_to(meta)`：把非空字段写回 ORM 对象（更新场景）
   - `to_conditions()`：返回 SQLAlchemy where 条件列表（查询场景）
   
   VO 只做序列化投影（`from_orm_obj`）。
3. **分页返回统一用 `Page[T]`**：通用分页容器，跨模块复用；`FileListVO` 即 `Page[FileVO]`。
4. **FileVO 保持最小**：只包含文件元信息（id、名称、大小、时间、分类），不含临时性字段。
5. **预览/下载走独立接口**：URL 生成和数据流不塞进 FileVO。
6. **统一接口 + 分类区分**：头像/证明材料/政策文件共用 `upload`/`update`/`search` 等端点，靠 `fileCategory` 字段区分逻辑分支。
7. **请求上下文由 Service 自行获取**：`user_id` / `permissions` / `roles` 等从 `ContextVar` 读取，**不通过路由层作为参数传入**。保持 Service 方法签名只依赖 Request/VO/业务 ID，路由层不成为"上下文搬运工"。
8. **Service 负责业务编排**：业务多步操作（事务边界、存储补偿、跨表更新、旧资源清理等）属 Service 职责，不是路由层职责，也不是 DTO 职责。
9. **事务边界由 Service 管理（已定稿）**

   Service 负责显式调用 `commit()` / `rollback()`，原因：
   - 多事务边界场景（如 `upload_avatar`：新记录提交 + 旧清理独立提交）需要 Service 精细控制
   - 依赖注入层（`get_db_session`）只管 session 生命周期（open / close），不参与事务

   > **设计决策**：本模块采用 Service 管理事务模式，已在 §13.5 记录架构决策。

> **判断口诀**：看到 Service 内出现"读 Request 字段 + 写 ORM 字段 + 判断字段是否非空"，就应当下沉到 DTO 的 `to_metadata` / `apply_to` / `to_conditions` 方法中。

## 2. 核心对象职责


| 对象                        | 所在层          | 职责                                                                                                  |
| ------------------------- | ------------ | --------------------------------------------------------------------------------------------------- |
| `FileUploadRequest`       | 路由 + Service | 三字段：`fileCategory` + `file` + `content`；校验 `fileCategory`；提供 `to_metadata(user_id)` 构造 ORM（计算 ext、key、所有 ORM 字段） |
| `FileAvatarUploadRequest` | 路由 + Service | 头像独立 Request；字段：`content` + `contentType`；提供 `to_metadata(user_id)` 构造 ORM（固定 jpg 后缀、按 user_id 命名）              |
| `FileUpdateRequest`       | 路由 + Service | 接收更新字段（仅 `originalName`）；提供 `apply_to(meta)` 方法把非空字段写回 ORM，service 不再判断字段是否非空                              |
| `FileQueryRequest`        | 路由 + Service | 接收分页/过滤参数；提供 `to_conditions()` 返回 SQLAlchemy where 条件列表，service 直接拼接过滤软删除条件即可                              |
| `search_files`            | Service      | 返回 `Page[FileVO]`，ORM→VO 转换在 service 层内部完成，不在路由层处理                                                          |
| `FileMetadata`            | Service + Model | 纯 ORM 对象，移除 `file_purpose`，11 个字段                                                                       |
| `FileVO`                  | 查询列表/详情返回    | 核心元信息投影（无 url），用于前端列表和详情展示                                                                              |
| `Page[T]`                 | 通用分页返回       | 跨模块复用的分页容器，`FileListVO = Page[FileVO]`，`search_files` 返回此类型                                              |
| `FileDataVO`              | 预览/下载场景返回    | 包含 `url`，专用于需要访问地址的场景                                                                                   |

## 3. VO 设计：FileVO / Page[T] / FileDataVO

### 3.1 为什么需要三个对象

**场景差异**：


| 场景                      | 需要的字段                     |
| ----------------------- | ------------------------- |
| 列表展示（search）            | 文件名、大小、时间、分类（**不需要 url**） |
| 详情展示（GET /{id}）         | 同列表（**不需要 url**）          |
| 预览/下载（preview/download） | 元信息 + url（**需要 url**）     |


**之前的问题**：用一个 VO 试图覆盖所有场景，导致：

- `url` 对列表/详情展示毫无意义
- 列表页每次查询都要额外计算 url（浪费）
- 混在一起字段来源不清晰

### 3.2 FileVO — 仅用于前端展示

```python
class FileVO(BaseModel):
    """文件元信息视图——仅包含文件本身的客观属性，供前端列表/详情展示"""
    model_config = ConfigDict(from_attributes=True)

    id: int                           # 主键
    originalName: str                  # 原始文件名
    fileSize: int                     # 字节数
    fileSizeFormatted: str             # 人类可读大小
    contentType: Optional[str]         # MIME 类型
    fileExtension: Optional[str]       # 后缀（不含点）
    fileCategory: str                  # AVATAR / PROOF / POLICY
    uploadUserId: int                  # 上传人 ID
    uploadTime: str                   # 上传时间（ISO 字符串）

    @classmethod
    def from_orm_obj(cls, obj) -> "FileVO":
        cat = obj.file_category.value if hasattr(obj.file_category, "value") else obj.file_category
        return cls(
            id=obj.id,
            originalName=obj.original_name,
            fileSize=obj.file_size,
            fileSizeFormatted=_format_size(obj.file_size),
            contentType=obj.content_type,
            fileExtension=obj.file_extension,
            fileCategory=cat,
            uploadUserId=obj.upload_user_id,
            uploadTime=str(obj.created_at),
        )
```

**不含 `url` 的原因**：列表页/详情页不需要访问地址，url 只在用户主动点击预览/下载时才需要，此时走独立接口获取。

### 3.3 Page[T] — 通用分页容器（`FileListVO = Page[FileVO]`）

`Page` 是跨模块复用的通用分页响应，`FileListVO` 只是它的文件模块特例（`Page[FileVO]`）。

```python
from typing import Generic, TypeVar, List
from pydantic import BaseModel

T = TypeVar("T")

class Page(BaseModel, Generic[T]):
    """通用分页响应容器"""
    list: List[T]        # 数据列表
    total: int           # 总记录数
    pageNum: int         # 当前页码
    pageSize: int        # 每页大小
    pages: int           # 总页数

    @classmethod
    def build(
        cls,
        items: List[T],
        total: int,
        page_num: int,
        page_size: int,
    ) -> "Page[T]":
        """构造分页响应，自动计算总页数"""
        pages = (total + page_size - 1) // page_size if total > 0 else 0
        return cls(
            list=items,
            total=total,
            pageNum=page_num,
            pageSize=page_size,
            pages=pages,
        )


# 文件模块别名（等义于 Page[FileVO]，直接使用 Page 亦可）
class FileListVO(Page[FileVO]):
    """文件分页查询结果——即 Page[FileVO]，两处完全等义"""
    pass
```

> **为什么用别名而非独立实现**：`FileListVO = Page[FileVO]`，结构完全一致，仅作为模块级语义标记，无需重复定义字段。

## 4. FileMetadata 模型（移除 file_purpose）

### 4.1 字段定义

```python
class FileMetadata(Base, TimestampMixin):
    """文件元数据表（11 字段）"""
    __tablename__ = "file_metadata"

    # ---- MinIO 定位 ----
    object_name: Mapped[str] = mapped_column(String(255), nullable=False, index=True)
        # MinIO object key，如 proof/2025/123/abc123def.pdf

    # ---- 原始信息 ----
    original_name: Mapped[str] = mapped_column(String(255), nullable=False)
    file_size: Mapped[int] = mapped_column(Integer, nullable=False)
    content_type: Mapped[Optional[str]] = mapped_column(String(100))
    file_extension: Mapped[Optional[str]] = mapped_column(String(10))

    # ---- 分类与归属（鉴权核心）----
    file_category: Mapped[FileCategory] = mapped_column(
        Enum(FileCategory, native_enum=False, length=20),
        nullable=False, index=True,
    )
    upload_user_id: Mapped[int] = mapped_column(Integer, nullable=False, index=True)

    # ---- 软删除 ----
    is_deleted: Mapped[bool] = mapped_column(Boolean, default=False, index=True)
    delete_time: Mapped[Optional[str]] = mapped_column(String(50))

    __table_args__ = (
        Index("ix_file_category_deleted", "file_category", "is_deleted"),
    )
```

### 5.1 schemas/file.py

```python
"""文件相关 DTO"""
from pydantic import BaseModel, Field, ConfigDict, field_validator
from fastapi import UploadFile, File
from typing import Optional, List, Generic, TypeVar
import uuid
from datetime import datetime

from src.models import FileCategory, FileMetadata


# ---- 通用分页容器（跨模块复用） ----

T = TypeVar("T")

class Page(BaseModel, Generic[T]):
    """通用分页响应容器"""
    list: List[T]
    total: int
    pageNum: int
    pageSize: int
    pages: int

    @classmethod

        cls,

        page_num: int,
        page_size: int,

        pages = (total + page_size - 1) // page_size if total > 0 else 0

# ---- 辅助函数（无状态，无 IO） ----

def _build_object_name(category: str, original_name: str, user_id: int) -> str:
    """生成 MinIO object key"""
    ext = ""
    if "." in original_name:
        ext = original_name.rsplit(".", 1)[-1].lower()
        if len(ext) > 10:
            ext = ext[:10]
    unique_id = uuid.uuid4().hex
    year = datetime.utcnow().year
    key = f"{category.lower()}/{year}/{user_id}/{unique_id}"
    return f"{key}.{ext}" if ext else key


def _format_size(size: Optional[int]) -> str:
    """人类友好的文件大小"""
    if size is None:
        return "-"
    if size < 1024:
        return f"{size}B"
    if size < 1024 * 1024:
        return f"{size / 1024:.1f}KB"
    return f"{size / (1024 * 1024):.1f}MB"


# ---- 请求 DTO ----

class FileUploadRequest(BaseModel):
    """文件上传请求（通用：PROOF / POLICY）"""
    fileCategory: str = Field(default="PROOF")
    file: UploadFile = File(...)
    content: bytes = Field(...)

    @field_validator("fileCategory")
    @classmethod
    def normalize_category(cls, v: str) -> str:
        return v.upper() if v else "PROOF"

    def to_metadata(self, user_id: int) -> FileMetadata:
        """根据本请求构造 ORM 对象

        派生逻辑全部封死在 DTO 中，service 仅落库：
        - original_name ← self.file.filename
        - ext          ← 从 original_name 取后缀
        - object_name  ← _build_object_name(fileCategory, original_name, user_id)
        - content_type ← self.file.content_type
        - file_size    ← len(self.content)
        - 其余字段    ← 直接传值
        """
        original_name = self.file.filename or "unnamed"
        ext = ""
        if "." in original_name:
            ext = original_name.rsplit(".", 1)[-1].lower()
            if len(ext) > 10:
                ext = ext[:10]
        key = _build_object_name(self.fileCategory, original_name, user_id)
        return FileMetadata(
            object_name=key,
            original_name=original_name,
            file_size=len(self.content),
            content_type=self.file.content_type or "application/octet-stream",
            file_extension=ext,
            file_category=FileCategory(self.fileCategory),
            upload_user_id=user_id,
        )


class FileAvatarUploadRequest(BaseModel):
    """头像上传请求（独立 Request，因为命名规则 / cleanup 逻辑不同）

    与通用上传的区别：
    - 固定为 AVATAR 分类
    - 文件名固定为 avatar_{user_id}.jpg（覆盖式而非 UUID）
    - service 端需要清理旧头像
    """
    content: bytes = Field(...)
    contentType: str = Field(default="image/jpeg")

    def to_metadata(self, user_id: int) -> FileMetadata:
        """构造头像 ORM 对象

        与通用上传差异：
        - file_category 固定为 AVATAR
        - object_name / original_name 按 user_id 命名（覆盖式，非 UUID）
        - file_extension 固定为 jpg
        """
        object_name = _build_object_name(
            FileCategory.AVATAR.value, f"avatar_{user_id}.jpg", user_id
        )
        return FileMetadata(
            object_name=object_name,
            original_name=f"avatar_{user_id}.jpg",
            file_size=len(self.content),
            content_type=self.contentType,
            file_extension="jpg",
            file_category=FileCategory.AVATAR,
            upload_user_id=user_id,
        )


class FileUpdateRequest(BaseModel):
    """文件元信息更新请求——DTO 承担'字段判断+写回'职责"""
    originalName: Optional[str] = Field(default=None)

    def apply_to(self, meta: FileMetadata) -> bool:
        """把非空字段写回 ORM，返回是否有字段被修改

        Service 调用后无需再判断 `req.originalName is not None`——
        '字段是否要更新' 的逻辑完全封死在 DTO 中。
        """
        changed = False
        if self.originalName is not None:
            meta.original_name = self.originalName
            changed = True
        return changed


class FileQueryRequest(BaseModel):
    """文件查询请求——DTO 承担'字段→ORM where 条件'翻译职责

    配置 `populate_by_name=True`：既支持驼峰字段名（`fileName`）也支持下划线（`file_name`）
    传入，使得 §5.3 描述的 `Annotated[FileQueryRequest, Query()]` 自动解析成为可能。
    """
    model_config = ConfigDict(populate_by_name=True)

    fileName: Optional[str] = Field(default=None, description="文件名模糊查询")
    fileCategory: Optional[str] = Field(default=None, description="文件分类")
    uploadUserId: Optional[int] = Field(default=None, description="上传用户 ID")
    startTime: Optional[str] = Field(default=None, description="开始时间（ISO8601）")
    endTime: Optional[str] = Field(default=None, description="结束时间（ISO8601）")
    pageNum: int = Field(default=1, ge=1, description="页码")
    pageSize: int = Field(default=20, ge=1, le=100, description="每页大小")

    def to_conditions(self) -> List:
        """把 Request 字段翻译成 SQLAlchemy where 条件列表

        Service 直接拼接软删除过滤即可：
            conditions = [FileMetadata.is_deleted == False, *req.to_conditions()]

        翻译规则（封死在 DTO 中）：
        - fileName     → original_name ILIKE
        - fileCategory → file_category 枚举匹配
        - uploadUserId → upload_user_id
        - startTime    → created_at >=
        - endTime      → created_at <=
        """
        conditions: List = []
        if self.fileName:
            conditions.append(FileMetadata.original_name.ilike(f"%{self.fileName}%"))
        if self.fileCategory:
            try:
                conditions.append(
                    FileMetadata.file_category == FileCategory(self.fileCategory.upper())
                )
            except ValueError:
                conditions.append(FileMetadata.file_category == self.fileCategory)
        if self.uploadUserId:
            conditions.append(FileMetadata.upload_user_id == self.uploadUserId)
        if self.startTime:
            conditions.append(FileMetadata.created_at >= self.startTime)
        if self.endTime:
            conditions.append(FileMetadata.created_at <= self.endTime)
        return conditions
```

### 5.3 Query DTO 的自动解析（推荐写法）

`FileQueryRequest` 仅含基本类型字段（无 `UploadFile`），可由 FastAPI 直接从 query string 解析——路由层不再 6 个参数 + 手动构造 Request：

```python
from typing import Annotated
from fastapi import Query, Depends

@router.get("/search")
async def search_files(
    req: Annotated[FileQueryRequest, Query()],
    service: FileService = Depends(get_file_service),
):
    page: FileListVO = await service.search_files(req)
    return R.success_resp(page.model_dump())
```

**前置条件**：

- `FileQueryRequest` 必须 `model_config = ConfigDict(populate_by_name=True)`（已在 §5.1 配置）
- 字段保留驼峰命名（`fileName` / `fileCategory` / `pageNum`），与前端 query 参数对齐
- 若字段改用下划线命名（`file_name`），需为每个字段加 `Field(..., alias="fileName")`

**限制**：含 `UploadFile` / `bytes` / 复杂对象的 Request 不可用此写法：

| Request                | 解析方式                          |
| ---------------------- | ----------------------------- |
| `FileQueryRequest`     | `Annotated[..., Query()]` ✅    |
| `FileUpdateRequest`    | `Annotated[..., Body()]` ✅    |
| `FileUploadRequest`    | `multipart/form-data + Depends 读取 bytes`  |
| `FileAvatarUploadRequest` | `multipart/form-data + Depends 读取 bytes` |

> **参数源对照**（按 HTTP 方法 + DTO 字段类型推导）：
>
> | HTTP 区域 | 标记           | 何时使用                              |
> | -------- | -------------- | ------------------------------------- |
> | URL query string | `Annotated[DTO, Query()]` | GET 端点 + DTO 全是基本字段 |
> | 请求体（JSON）  | `Annotated[DTO, Body()]`  | PUT/POST 端点 + DTO 全是基本字段 |
> | 请求体（multipart） | `File()` / `Depends()` | DTO 含 `UploadFile` / `bytes`（FastAPI 硬约束） |

> **判断口诀**：`Annotated` 三件套（`Query()`/`Body()`/`File()`）的选择**只看 DTO 的字段清单**——
> DTO 没有 FastAPI 特殊类型 → `Annotated[DTO, X()]` 一行搞定；含 `UploadFile` / `bytes` → 必须路由层手工组装。

> **v5.2 升级后**：`update_file` 已迁移到 `Annotated[FileUpdateRequest, Body()]`，§9 给出完整示例。
> **历史背景**：§9 路由示例早期用"散落参数 + 手动构造 Request"的写法以保持与基础版兼容；v5.2 起已全部迁移到 `Annotated` 三件套。

### 5.4 PUT 端点的 Body 自动解析（`Annotated[DTO, Body()]`）

`FileUpdateRequest` 同样仅含基本类型字段（无 `UploadFile`），可由 FastAPI 从 JSON body 直接解析——路由层签名仅含 `Annotated[DTO, Body()]` 即可，不再需要裸类型：

```python
from typing import Annotated
from fastapi import Body, Depends

@router.put("/{file_id}")
async def update_file(
    file_id: int,
    req: Annotated[FileUpdateRequest, Body()],
    service: FileService = Depends(get_file_service),
):
    """更新文件元信息（仅支持更新 originalName）"""
    meta = await service.update_file(req, file_id)
    return R.success_resp(FileVO.from_orm_obj(meta).model_dump())
```

**显式标注 `Body()` 的三个理由**：

1. **OpenAPI 文档准确**：不写 `Body()` 时，FastAPI 依赖"非 Query 路径的 BaseModel 默认走 Body"的推断生成 schema；显式标注使文档明确标记 request body。
2. **避免未来 GET → PUT/PATCH 切换时的隐性坑**：将来若把 `update_file` 改回 GET（少见但可能），缺省标注会让框架仍然误把它当 body 解析。
3. **与 `Annotated[DTO, Query()]` 写法风格统一**：所有"DTO 全是基本字段"的端点统一显式标注，便于 codegen 工具识别协议类型。

**完整路由签名风格**（v5.2 起路由层统一遵循的三种形态）：

| HTTP 方法 | DTO 字段类型            | 路由签名写法                                  |
| ---------- | ----------------------- | --------------------------------------------- |
| GET        | 全是 Pydantic 基本字段 | `Annotated[DTO, Query()]`                   |
| PUT/POST   | 全是 Pydantic 基本字段  | `Annotated[DTO, Body()]`                    |
| POST       | 含 `UploadFile` / `bytes` | 路由层手工组装 DTO（FastAPI 协议层硬约束） |

头像上传与其他文件上传的**核心差异**在于"新头像替换旧头像"的 cleanup 逻辑：

- 其他文件：直接新增，不清理旧文件（历史记录需保留）
- 头像文件：每人只有一个，新上传后旧头像需软删除 + MinIO 清理

这个 cleanup 逻辑如果塞进统一的 `upload` 接口，需要在 service 中额外判断 `fileCategory == AVATAR`，逻辑耦合。故头像保留独立端点 `/api/file/avatar`，与其他文件的处理完全隔离。

## 8. Service 层完整代码

```python
import io
from datetime import datetime, timedelta
from typing import List, Optional, Tuple

from sqlalchemy import func, select
from sqlalchemy.ext.asyncio import AsyncSession

from src.app.context import get_user_id
from src.infra.storage.base import Storage
from src.models import FileCategory, FileMetadata
from src.app.schemas import (
    FileUploadRequest,
    FileAvatarUploadRequest,
    FileUpdateRequest,
    FileQueryRequest,
    FileVO,
    FileListVO,
)


# ========== 异常类型 ==========

class _BusinessError(Exception):
    http_code: int = 500
    default_message: str = "服务器内部错误"

    def __init__(self, *args):
        if len(args) == 0:
            self.message = self.default_message
        elif len(args) == 1:
            self.message = str(args[0])
        else:
            self.message = self.default_message
        super().__init__(self.message)


class FileNotFoundError(_BusinessError):
    http_code = 404
    default_message = "文件不存在"


class FileForbiddenError(_BusinessError):
    http_code = 403
    default_message = "无权访问该文件"


# ========== FileService ==========

class FileService:

    def __init__(self, db: AsyncSession, storage: Storage):
        self._db = db
        self._storage = storage

    # ---- 上传 ----

    async def upload_file(self, req: FileUploadRequest) -> Tuple[FileMetadata, str]:
        """通用文件上传：DTO 构造 ORM → MinIO 写 → DB 写（DB 失败则回滚 MinIO）

        事务归属：service 显式 commit（参见 §1 原则 9）
        """
        user_id = get_user_id()
        metadata = req.to_metadata(user_id)
        key = metadata.object_name

        await self._storage.upload(
            file_obj=io.BytesIO(req.content),
            key=key,
            content_type=metadata.content_type,
        )

        self._db.add(metadata)
        try:
            await self._db.commit()
        except Exception:
            await self._safe_delete(key, ignore_error=False)
            await self._db.rollback()
            raise
        await self._db.refresh(metadata)

        return metadata, self._storage.get_access_url(key)

    async def upload_avatar(
        self,
        req: FileAvatarUploadRequest,
    ) -> Tuple[FileMetadata, str]:
        """头像上传：DTO 构造 ORM → 旧头像清理 → 新头像写入

        事务拆解：
        - 事务 1：写入新头像（commit 失败 → 回滚 + 删 MinIO）
        - 事务 2：标记旧头像 is_deleted（commit 失败不影响事务 1 已成功的状态）

        注意：service 不再手工算 ext/命名/拼 ORM，全部由 req.to_metadata() 完成。
        """
        user_id = get_user_id()
        new_meta = req.to_metadata(user_id)

        # 找旧头像
        old: Optional[FileMetadata] = (await self._db.execute(
            select(FileMetadata).where(
                FileMetadata.file_category == FileCategory.AVATAR,
                FileMetadata.upload_user_id == user_id,
                FileMetadata.is_deleted == False,
            )
        )).scalar_one_or_none()

        # 上传新头像
        await self._storage.upload(
            io.BytesIO(req.content),
            key=new_meta.object_name,
            content_type=new_meta.content_type,
        )

        # 事务 1：写新记录
        self._db.add(new_meta)
        try:
            await self._db.commit()
        except Exception:
            await self._safe_delete(new_meta.object_name, ignore_error=False)
            await self._db.rollback()
            raise
        await self._db.refresh(new_meta)

        # 事务 2：清理旧头像（独立事务，不阻塞主流程）
        if old and old.object_name != new_meta.object_name:
            old.is_deleted = True
            old.delete_time = datetime.utcnow().isoformat()
            try:
                await self._db.commit()
                await self._safe_delete(old.object_name, ignore_error=True)
            except Exception:
                await self._db.rollback()

        return new_meta, self._storage.get_access_url(new_meta.object_name)

    # ---- 查询（统一入口 get_file） ----

    async def get_file(self, file_id: int) -> FileMetadata:
        """获取文件——单一入口，不存在则抛 FileNotFoundError

        所有按 id 查询都走这个方法；不再保留 get_file_by_id(Optional 版本)，
        避免双方法职责重复。
        """
        result = await self._db.execute(
            select(FileMetadata).where(
                FileMetadata.id == file_id,
                FileMetadata.is_deleted == False,
            )
        )
        meta = result.scalar_one_or_none()
        if not meta:
            raise FileNotFoundError(f"file_id={file_id}")
        return meta

    async def search_files(self, req: FileQueryRequest) -> FileListVO:
        """分页搜索：DTO 翻译 where → count → 分页 → ORM→VO

        注意：service 不再'读 Request 字段 → 拼 where'，由 req.to_conditions() 一次性翻译。
        """
        conditions = [FileMetadata.is_deleted == False, *req.to_conditions()]

        # 计数
        count_result = await self._db.execute(
            select(func.count()).select_from(FileMetadata).where(*conditions)
        )
        total = count_result.scalar() or 0

        # 分页查询
        query = (
            select(FileMetadata)
            .where(*conditions)
            .order_by(FileMetadata.created_at.desc())
            .offset((req.pageNum - 1) * req.pageSize)
            .limit(req.pageSize)
        )
        result = await self._db.execute(query)
        files = list(result.scalars().all())

        # ORM → VO + 分页封装，全在 service 层完成
        return FileListVO.build(
            items=[FileVO.from_orm_obj(f) for f in files],
            total=total,
            page_num=req.pageNum,
            page_size=req.pageSize,
        )

    # ---- 预览 / 下载 ----

    async def get_preview_data(
        self,
        file_id: int,
        expiry_minutes: int = 60,
    ) -> Tuple[FileMetadata, str]:
        """返回 (meta, url)——供路由构造 FileDataVO

        参数 expiry_minutes 控制 MinIO 预签名 URL 的过期时间（1~1440 分钟）。
        """
        meta = await self.get_file(file_id)
        url = self._storage.get_access_url(
            meta.object_name,
            expires=timedelta(minutes=expiry_minutes),
        )
        return meta, url

    async def get_download_stream(self, file_id: int) -> Tuple[bytes, str, str]:
        """返回 (bytes, content_type, original_name)"""
        meta = await self.get_file(file_id)
        data = await self._storage.download(meta.object_name)
        return data, meta.content_type or "application/octet-stream", meta.original_name

    # ---- 更新 / 删除 ----

    async def update_file(self, req: FileUpdateRequest, file_id: int) -> FileMetadata:
        """更新文件元信息：DTO 写回 ORM，无字段判断逻辑

        注意：service 不再'if req.originalName is not None'，由 req.apply_to(meta) 封装。
        """
        meta = await self.get_file(file_id)
        if not req.apply_to(meta):
            return meta  # 无字段被修改，直接返回（不触发 commit）
        await self._db.commit()
        await self._db.refresh(meta)
        return meta

    async def delete_file(self, file_id: int) -> None:
        """软删除"""
        meta = await self.get_file(file_id)
        meta.is_deleted = True
        meta.delete_time = datetime.utcnow().isoformat()
        await self._db.commit()

    # ---- 内部辅助 ----

    async def _safe_delete(self, key: str, ignore_error: bool = True) -> None:
        """MinIO 删除——失败时是否抛异常由 ignore_error 控制

        Args:
            key: 对象键名
            ignore_error: True=失败仅记录日志（用于清理旧头像等不阻塞主流程的场景）；
                          False=失败抛异常（用于补偿删除，需要外层 catch）。
        """
        try:
            await self._storage.delete(key)
        except Exception as e:
            if ignore_error:
                print(f"[FileService] MinIO 删除失败（忽略）: {key} - {e}")
            else:
                print(f"[FileService] MinIO 补偿删除失败: {key} - {e}")
                raise
```

## 9. 路由层完整代码

> **v5.2 重要变更**：路由层已全面迁移到 `Annotated` 三件套（§5.3 §5.4）——
> `search_files` 用 `Annotated[..., Query()]`，`update_file` 用 `Annotated[..., Body()]`，
> `upload` / `avatar` 因含 `UploadFile` / `bytes` 必须手工组装 DTO（FastAPI 协议层硬约束）。

> **任何新增端点都必须按 §5.4 表格的"路由签名风格"三选一，不得混用其他写法。**

```python
"""文件路由

设计原则（docs/file/分层设计.md §1）：
- 路由层只做：参数收集、DTO 构造、调用 service、序列化返回
- 不做任何 ORM 字段编辑、不再调 storage、不再判空
- Service 显式管理事务（§13.5 架构决策）
- 路由签名遵循 §5.4 表格三种形态（Annotated Query / Annotated Body / 手工组装）
"""
import io
from typing import Annotated
from urllib.parse import quote

from fastapi import APIRouter, Body, Depends, File, Query, UploadFile
from fastapi.responses import StreamingResponse

from src.app.dependencies import get_file_service
from src.app import response as R
from src.app.schemas import (
    FileUploadRequest,
    FileAvatarUploadRequest,
    FileUpdateRequest,
    FileQueryRequest,
    FileVO,
    FileDataVO,
)
from src.services.file_service import FileService

router = APIRouter(prefix="/api/file", tags=["文件"])


# ---- 内部辅助（仅与 HTTP 协议相关） ----

async def _read_and_validate_size(file: UploadFile = File(...)) -> bytes:
    """读取文件字节并校验大小 → 超过限制抛 HTTP 413"""
    from src.infra.config import get_settings
    from fastapi import HTTPException, status

    settings = get_settings()
    content = await file.read()
    if len(content) > settings.MAX_FILE_SIZE:
        raise HTTPException(
            status_code=status.HTTP_413_REQUEST_ENTITY_TOO_LARGE,
            detail=f"文件大小不能超过 {settings.MAX_FILE_SIZE // (1024*1024)}MB",
        )
    return content


def _streaming_response(file_data: bytes, content_type: str, original_name: str):
    """文件下载流（HTTP 协议层封装）"""
    encoded_name = quote(original_name, safe='')
    return StreamingResponse(
        io.BytesIO(file_data),
        media_type=content_type,
        headers={
            "Content-Disposition": f"attachment; filename*=UTF-8''{encoded_name}",
        },
    )


# ============ 1. 上传（multipart → 必须手工组装） ============

@router.post("/upload", status_code=201)
async def upload_file(
    content: bytes = Depends(_read_and_validate_size),
    file: UploadFile = File(..., description="上传文件"),
    fileCategory: str = Query("PROOF"),
    service: FileService = Depends(get_file_service),
):
    """通用文件上传（按 fileCategory 分类：PROOF / POLICY）

    含 UploadFile + bytes → 路由层手工组装 FileUploadRequest（§5.4 手工组装形态）。
    """
```

## 11. contextvar 与 response.py 用法

### 11.1 contextvar（不变，但使用边界明确）

```python
# 中间件写入
from src.app.context import set_user, get_user_id

set_user({"user_id": user_id, "username": ..., "permissions": [...]})
```

## 12. 通用分页容器：Page[T]

### 12.1 为什么需要 Page[T]

此前每个模块的分页返回结构散落在各处（字段名不一致、`pages` 计算重复），`Page[T]` 提供跨模块统一接口。

### 12.2 核心能力

- **泛型 `T`**：任一 VO 类型均可作为列表项，如 `Page[FileVO]`、`Page[UserVO]`
- **`build()` 工厂方法**：自动计算 `pages`，调用方只需传入原始数据
- **字段最少化**：仅含 `list / total / pageNum / pageSize / pages` 五个字段

### 12.3 使用方式

`Page.build()` 在 **Service 层** 调用（不在路由层），路由层只透传 `Page` 对象给 `R.success_resp()`。

```python
# schemas/file.py
class FileListVO(Page[FileVO]):
    """文件分页 = Page[FileVO]，两处等义"""
    pass

# service 层（数据封装下沉）
async def search_files(self, req: FileQueryRequest) -> FileListVO:
    # ... SQLAlchemy 查询 ...
    files, total = ..., ...
    return FileListVO.build(
        items=[FileVO.from_orm_obj(f) for f in files],
        total=total,
        page_num=req.pageNum,
        page_size=req.pageSize,
    )

# 路由层（仅透传，不碰数据）
@router.get("/search")
async def search_files(req: FileQueryRequest, service: FileService = Depends(...)):
    page: FileListVO = await service.search_files(req)
    return R.success_resp(page.model_dump())
```

### 12.4 各模块复用

| 模块   | 分页类型别名          | 等义于           |
| ---- | ---------------- | ------------- |
| 文件   | `FileListVO`     | `Page[FileVO]` |
| 用户   | `UserListVO`     | `Page[UserVO]` |
| 政策   | `PolicyListVO`   | `Page[PolicyVO]` |

只需在各模块的 `schemas/xx.py` 中定义 `XxxListVO(Page[XxxVO])`，无需重复字段定义。

## 13. 遗留问题

### 13.1 `file_purpose` 是否真的不需要？

当前 `file_purpose` 仅作为"业务描述"存在（如"加分证明材料"），对系统功能没有任何实际影响。如果业务方后续需要这个字段，可以加回。但当前版本从 Model → DTO → Service 全链路移除，保持最小化。

### 13.2 头像端点是否可以合并？

理论上头像上传可以合并到 `/api/file/upload` + `fileCategory=AVATAR`，在 service 层加 cleanup 判断。但这样会导致上传接口承担两种不同语义（新增 vs 替换），增加理解和测试复杂度。当前保留独立端点是更清晰的选择。

### 13.3 预览/下载是否需要鉴权？

当前实现中预览和下载不做业务鉴权（CRUD 阶段）。`user_id` 和 `user_permissions` 参数已传入，后续在 PROOF 类型文件上接入 `_check_proof_access` 三表 JOIN 鉴权即可。

### 13.4 路由层为什么不再传 `user_id`？

按 §1 原则 7，路由层不应该成为"上下文搬运工"——`user_id` 等请求上下文应由 service 通过 ContextVar 自取。这带来三个好处：
1. **路由层函数签名更纯**：只依赖 Request/VO/业务 ID，不被上下文污染
2. **Service 更易复用**：从 HTTP 调用切到定时任务 / 内部 RPC 时，无需改签名
3. **测试更简单**：service 单元测试时只需 `set_user(...)` 设置 ContextVar，不必伪造请求

代价：service 内每次都调用 `get_user_id()`，但 ContextVar 是 O(1) 读取，开销可忽略。

### 13.5 架构决策：为什么不用依赖注入层统一管理事务？

**决策**：Service 显式管理事务（commit/rollback），依赖注入层只管理 session 生命周期。

**原因**：
1. **多事务边界**：`upload_avatar` 需要先提交新头像，再独立提交旧头像清理（清理失败不影响主流程）
2. **Saga 补偿模式**：跨存储（MinIO + DB）的补偿删除需要在事务失败时立即执行，Service 层能精准控制时机
3. **测试可验证**：显式 commit 使单元测试更容易验证事务边界

**已评估的替代方案**：依赖注入层 try/except 统一提交/回滚（常见 FastAPI 模式）
- 优点：Service 更纯粹，不感知事务
- 缺点：无法处理多事务边界，需要拆成多个 session 或引入 Saga 编排，复杂度更高

**结论**：当前方案是权衡后的合理选择，不视为"架构债"。

### 13.6 路由签名风格是否会出现第四种形态？

**决策**：不允许。

**已锁定的三种路由签名形态**（见 §5.4）：

1. `Annotated[DTO, Query()]` — GET + DTO 全是基本字段
2. `Annotated[DTO, Body()]` — PUT/POST + DTO 全是基本字段
3. 手工组装 DTO — POST + DTO 含 `UploadFile` / `bytes`

**不允许出现的写法**：

| ❌ 禁止写法 | 原因 |
| ---------- | ---- |
| 散落 `Query()` 参数 + 手动组装 DTO（v5.0 风格） | 已全部迁移到 `Annotated` 三件套，§10.5 对比说明 |
| `body: FileUpdateRequest` 裸类型 | 缺省标注会让框架依赖"非 Query 路径的 BaseModel 默认走 Body"的推断生成 schema，OpenAPI 文档不准确，且未来 GET → PUT/PATCH 切换可能踩坑 |
| `Annotated[DTO, Form()]` 包装 multipart 字段 | Form() 不识别 UploadFile，Pydantic 不会接管 multipart 解析，是社区 hack，稳定性差 |
| service 方法直接挂在 router 上（`add_api_route`） | service 层被迫知道 HTTP 协议，违反 §1 原则 8（Service 负责业务编排，不感知协议） |

**判断标准**：编写新端点时，先看 DTO 的字段清单——若有 `UploadFile` / `bytes` → 走第 3 种；否则按 HTTP 方法选第 1 / 2 种。

> **为什么不把这块封进路由层抽象**：当前 8 个端点对应 3 种形态，再多一层抽象会增加调试栈而减少的代码量是有限的——见 §1 原则 1（Service 极度精简）。
