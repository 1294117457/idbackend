## 设计原则

**Template 系统只做一件事：基于证明材料计算加分。**

四六级成绩、游泳等级等资质信息不属于加分计算范畴，由管理员直接录入 `user.extra_info`，不走申请审批流程。

---

## 一、总览

```
TemplateCategory  →  Template  →  Application  →  ScoreData
（分类树 + 上限）    （计分规则）    （申请流水）       （通过的流水）
                                                        ↓
                                               User.score_info（汇总快照）
```

## 二、数据对象设计

### 1. TemplateCategory（分类树）

职责：定义分类层级和各级分值上限，纯配置数据。`is_bind_template` 字段**唯一作用**是标识"该节点已绑定 Template"，与子分类/性能优化无关。

```sql
CREATE TABLE template_category (
    id          SERIAL PRIMARY KEY,
    name        VARCHAR(100) NOT NULL,
    parent_id   INTEGER REFERENCES template_category(id),
    max_score   DECIMAL(5,2) NOT NULL CHECK (max_score >= 0),  -- 不允许 null（每级必须有上限）
    is_bind_template BOOLEAN DEFAULT FALSE, -- TRUE=已绑 template；FALSE=未绑 template（可绑可加子）
    sort_order      INTEGER DEFAULT 0,   -- 由管理员手动指定，未指定的视为 0，列表展示时排同级末尾
    is_active   BOOLEAN DEFAULT TRUE,
    description VARCHAR(255),
    created_at  TIMESTAMP,
    updated_at  TIMESTAMP
);
```

**示例数据：**

```
id | name     | parent_id | max_score | is_bind_template | sort_order
 1 | 加分总计  | null      | 100.00    | FALSE   | 1
 2 | 学业加分  | 1         | 60.00     | FALSE   | 1
 3 | 专长加分  | 1         | 20.00     | TRUE    | 2       ← 可绑 template（可绑多个）
 4 | 劳动教育  | 1         | 20.00     | TRUE    | 3       ← 可绑 template（可绑多个）
 5 | 竞赛奖项  | 2         | 20.00     | TRUE    | 1       ← 可绑 template（可绑多个）
 6 | 学术论文  | 2         | 10.00     | TRUE    | 2       ← 可绑 template（可绑多个）
```

> 同级展示顺序：`ORDER BY sort_order ASC, id ASC`（sort_order=0 视为排在同级末尾但 id 升序保稳定）。

**is_bind_template 状态机（v2，仅服务于"能否绑 template + 能否加子"）：**

```
is_bind_template=FALSE  → 未绑 template（可绑 template，可加子分类）
is_bind_template=TRUE   → 已绑 template（不可绑更多，不可加子）
```

`is_bind_template` 仅表示"是否已绑 template"，与子分类数量、template 数量、性能优化都无关：

- 创建分类时：新节点默认 `is_bind_template=FALSE`
- 绑定 template 时：由 `TemplateService.create` 显式调用 `bind_template()` 翻为 TRUE
- 添加子分类时：校验父节点 `is_bind_template=FALSE`（未绑 template），无父子数量限制
- 删除 template 时：由 `TemplateService.delete` 检查剩余数量归零后调 `unbind_template()` 翻回 FALSE
- 删除分类时：级联删除所有子分类与绑定的 template（DB CASCADE）；无需回滚父 flag

**校验规则：**

- 绑定 template 时：分类 `is_bind_template=FALSE` 才能绑；绑后翻 TRUE
- 添加子分类时：父节点必须 `is_bind_template=FALSE`，无父子数量限制
- 删除分类时：**级联删除所有子分类与绑定的 template**（前端管理界面在删除前做强提醒，确认后执行）
- `max_score` NOT NULL 且 `>= 0`（DB 层 CHECK）
- **不校验**子分类 `max_score` 之和与父 `max_score` 的关系——子分类分数之和由 `recalculate` 步骤的 `min(∑, 父 max_score)` 自然封顶
- **不提供**修改父节点（move / change_parent）能力，要调整位置只能"删除旧节点 + 新建子节点"

**删除的级联策略（DB 层）：**

```sql
-- template.category_id 改为 ON DELETE CASCADE：分类被删时 template 一起删
ALTER TABLE template
    DROP CONSTRAINT fk_template_category_old,
    ADD CONSTRAINT fk_template_category
        FOREIGN KEY (category_id) REFERENCES template_category(id)
        ON DELETE CASCADE;
```

template 被级联删除后，下挂的 rule / template_rule / rule_attribute 不受影响（template 不引用 attribute，rule / attribute 是独立的可复用字典数据）。

> application 历史不受影响：application 通过 `template_id` 外键引用 template，template 被级联删除时若 application 存在，会失败——这种情况由 service 层在删除前预检"该分类下是否有未关闭的 application"，若有则禁止删除（保守策略，避免历史被误删）。

**is_active 软启用：**

- `is_active=FALSE` 的分类在 `get_tree` 中不返回（管理端看不到、学生端选择不到）
- 不影响历史 application：application 在生成时已快照 `template_name/template_id/category_id` 等字段，score_data 与 application 的关联不受分类失效影响
- 失效分类下的历史 score_data 仍参与 `recalculate` 聚合（按历史快照 category_id 归类），只有该分类被硬删除才会清理

### 2. Template（计分模板）

职责：定义具体的计分逻辑，聚合 Rule 和 Attribute，是计算引擎的入口。

共 5 张表，结构参考 RBAC 的 user → role → permission 三层解耦方式：

```
template ──< template_rule >── rule ──< rule_attribute >── attribute
```

一个 template 可以绑定**多个** rule（多选/多填场景），本设计**不在 service 层校验** rule 之间的冲突（例如互斥/必填），由后台管理员配置时自行注意。

---

#### 表1：template（聚合根）

```sql
CREATE TABLE template (
    id            SERIAL PRIMARY KEY,
    name          VARCHAR(100) NOT NULL,
    category_id   INTEGER NOT NULL REFERENCES template_category(id) ON DELETE CASCADE,  -- 只绑叶子节点，分类被删时级联删除 template
    max_score     DECIMAL(5,2) NOT NULL,   -- 本模板单次申请上限（独立封顶，与所属分类 max_score 无关）
    sort_order    INTEGER DEFAULT 0,
    description   TEXT,
    review_count  INTEGER DEFAULT 1,
    is_active     BOOLEAN DEFAULT TRUE,
    created_at    TIMESTAMP,
    updated_at    TIMESTAMP
);
```

---

#### 表2：rule（选项组，可复用）

一个 rule = 前端一个选择组（下拉框）或输入组。rule 独立存在，可被多个 template 复用。

```sql
CREATE TABLE rule (
    id          SERIAL PRIMARY KEY,
    type        VARCHAR(20) NOT NULL
                CHECK (type IN ('CONDITION', 'TRANSFORM')),  -- 与 attribute.type 联动，决定 UI 渲染 / score 语义 / 绑定一致性
    score       DECIMAL(5,2),                  -- CONDITION 模式下此 rule 被选中时的得分；TRANSFORM 模式必须为 NULL
    name        VARCHAR(100) NOT NULL,
    sort_order  INTEGER DEFAULT 0,             -- rule 在所有 template 中的全局显示顺序（同一 rule 跨 template 顺序一致）
    description TEXT,
    is_active   BOOLEAN DEFAULT TRUE,
    created_at  TIMESTAMP,
    updated_at  TIMESTAMP
);
```

**`type` 字段（v4 新增）：**

| 用途 | 说明 |
|---|---|
| 决定 UI 渲染 | `CONDITION` → 下拉框 / 多选框；`TRANSFORM` → 数值输入框 |
| 决定 score 语义 | `CONDITION` → score 必填；`TRANSFORM` → score 必须 NULL |
| 决定 attribute 绑定一致性 | 绑 attribute 时 service 校验 `rule.type == attribute.type`（1 行） |

**`type` 与 `score` 的对应关系（service 层校验）：**

| rule.type | rule.score 取值 | 含义 |
|---|---|---|
| `CONDITION` | 必填（float） | 选中该 rule 对应的 attribute 后加 `rule.score` 分 |
| `TRANSFORM` | 必须为 NULL | 分数由 attribute.value 公式动态计算 |

**`score` 字段语义（service 层校验）：**

| Rule 绑定的所有 Attribute.type | rule.score 取值 | 含义 |
|---|---|---|
| 全部 CONDITION | 必填（float） | 选中该 rule 对应的 attribute 后加 `rule.score` 分 |
| 全部 TRANSFORM | 必须为 NULL | 分数由 attribute.value 公式动态计算 |
| 混合 CONDITION + TRANSFORM | 禁止（service 层拒绝） | 语义混乱 |

> 注意：本设计目前**未给 rule 设置 `is_required` 字段**。`ScoreCalculationService.calculate()` 对未选 rule 采取 `skip`（不参与计分）的策略。如未来需要必填语义，在 rule 表新增 `is_required BOOLEAN DEFAULT FALSE` 并在 calculate 与提交校验中加判断。

> 注意：template **不加** `type` 字段——ACM、综测类业务模板合法混用 CONDITION + TRANSFORM rule。`TemplateService.bind_rule` 不校验 type 一致性，仅返回 `is_mixed_type` 软提示给前端。

---

#### 表3：attribute（计算属性，可复用）

一个 attribute = 下拉框中的一个选项，或一段区间公式。attribute 独立存在，可被多个 rule 复用。

**类型由 `type` 显式声明：**

- `CONDITION`：value 为空字符串 `""`，分数下沉到 `rule.score`（同一 rule 下选中任意一个 attribute 都加 `rule.score`）
- `TRANSFORM`：value 为公式字符串（如 `"input * 0.5"`），用户输入数值后套公式计算，配合 `input_min`/`input_max` 限定区间（**半开半闭**：`input_min <= input < input_max`）

**前端按 `group_code` 分组渲染：**

- `group_code`：技术 key（如 `"award_lv"`），用于 SQL GROUP BY 与"+ 添加选项"按钮自动继承
- `group_name`：显示名（如 `"奖项等级"`），admin 后台可改
- 同一 `group_code` 的所有 attribute 必须共享同一 `group_name`（service 层强约束）

```sql
CREATE TABLE attribute (
    id          SERIAL PRIMARY KEY,
    name        VARCHAR(100) NOT NULL,    -- 选项显示名，如"国家级"、"0-60学分"
    group_code  VARCHAR(50) NOT NULL,     -- 技术 key，用于前端 GROUP BY 与添加同组 attribute 自动继承
    group_name  VARCHAR(100) NOT NULL,    -- 显示名，admin 后台可改
    type        VARCHAR(20) NOT NULL
                CHECK (type IN ('CONDITION', 'TRANSFORM')),
    value       TEXT,                     -- CONDITION: "" / TRANSFORM: 公式（含 input 变量）
    input_min   DECIMAL(10,4),            -- TRANSFORM 半开半闭下限（null = 无限制；匹配语义 >=）
    input_max   DECIMAL(10,4),            -- TRANSFORM 半开半闭上限（null = 无限制；匹配语义 <）
    sort_order  INTEGER DEFAULT 0,        -- attribute 在同 group 内的显示顺序
    description TEXT,                     -- 公式说明等备注
    is_active   BOOLEAN DEFAULT TRUE,
    created_at  TIMESTAMP,
    updated_at  TIMESTAMP
);

CREATE INDEX idx_attribute_group ON attribute(group_code);
```

**attribute 校验（在 service 层 `AttributeService.validate()`）：**

- `type` 必须是 `CONDITION` 或 `TRANSFORM`（枚举）
- 同一 `group_code` 的所有 attribute 必须共享同一 `group_name`（创建时若 group_code 已存在，强制覆盖 group_name）
- `CONDITION`：`value` 必须为空字符串 `""`（分数不在 attribute 上，而在 `rule.score`）
- `TRANSFORM`：`value` 必须只包含 `0-9 + - * / ** ( ) .` 和变量名 `input`（禁止函数调用、禁止内置名如 `sum/max/min`）
- `input_min`/`input_max`：允许 null；非 null 时 `input_min >= 0`；当两者都非 null 时 `input_min < input_max`

**rule ↔ attribute 绑定校验（在 service 层 `RuleService.bind_attribute()`，v4 新增）：**

- 唯一硬校验：**`rule.type == attribute.type`**（1 行，无 N+1）
- 由这条校验自然保证"同一 rule 内 attribute 不可 CONDITION+TRANSFORM 混用"——rule.type 一旦确定，所有绑上来的 attribute.type 必须与之一致
- 拒绝时的错误信息明确指出类型不匹配，不允许"增量混用"

**attribute 删除行为：**

attribute 的修改/删除**不影响**已有 application（application 只通过 `template.apply_score` 引用 template，与 attribute 无直接外键关联）。删除 attribute 时直接删除，**无 DB 级 ON DELETE 限制**；如果该 attribute 还被某条 `rule_attribute` 引用，由 service 层在删除前清理该关联（`rule_attribute.attribute_id` 级联删除，但 application 历史不受影响）。

---

#### 表4：template_rule（template-rule 多对多）

极简关联表，仅承载"template 绑定了哪些 rule"的事实，**不带 sort_order**（rule 全局排序由 `rule.sort_order` 决定）。

```sql
CREATE TABLE template_rule (
    id          SERIAL PRIMARY KEY,
    template_id INTEGER NOT NULL REFERENCES template(id) ON DELETE CASCADE,
    rule_id     INTEGER NOT NULL REFERENCES rule(id),
    created_at  TIMESTAMP,
    updated_at  TIMESTAMP,
    UNIQUE (template_id, rule_id)
);

CREATE INDEX idx_template_rule_template ON template_rule(template_id);
```

---

#### 表5：rule_attribute（rule-attribute 多对多）

极简关联表，仅承载"rule 绑定了哪些 attribute"的事实，**不带 sort_order**（attribute 排序由 `attribute.sort_order` 决定）。

```sql
CREATE TABLE rule_attribute (
    id           SERIAL PRIMARY KEY,
    rule_id      INTEGER NOT NULL REFERENCES rule(id) ON DELETE CASCADE,
    attribute_id INTEGER NOT NULL REFERENCES attribute(id) ON DELETE CASCADE,
    created_at   TIMESTAMP,
    updated_at   TIMESTAMP,
    UNIQUE (rule_id, attribute_id)
);

CREATE INDEX idx_rule_attribute_rule ON rule_attribute(rule_id);
```

**示例一：条件选择（竞赛奖项）**

注意：CONDITION 模式下 attribute.value 为空字符串 `""`，分数下沉到 `rule.score`。

```
template(name="竞赛奖项", category_id=学业加分, max_score=10)
  └── rule(name="奖项等级", type=CONDITION, score=5)              ← 前端下拉框，用户选一项，加 5 分
        ├── attribute(group_code="award_lv", group_name="奖项等级", type=CONDITION, name="国家级", value="")
        ├── attribute(group_code="award_lv", group_name="奖项等级", type=CONDITION, name="省级",   value="")
        └── attribute(group_code="award_lv", group_name="奖项等级", type=CONDITION, name="院级",   value="")
```

**示例一.5：ACM 模板（CONDITION + TRANSFORM 混用，template 不加 type 字段）**

业务合法场景：template 混用不同 type 的 rule（template **不加** type 字段）。

```
template(name="ACM竞赛综合加分", category_id=学业加分, max_score=20)  ← template 无 type 字段
  ├── rule(name="奖项等级",  type=CONDITION, score=10)  ↔ 绑 CONDITION attribute ✅
  │     └── attribute(group_code="award_lv", type=CONDITION, name="国家级", value="")
  ├── rule(name="代码量",    type=TRANSFORM, score=None) ↔ 绑 TRANSFORM attribute ✅
  │     └── attribute(group_code="code_lines", type=TRANSFORM, name="代码量", value="input * 0.05")
  └── rule(name="团队角色",  type=CONDITION, score=5)   ↔ 绑 CONDITION attribute ✅
        └── attribute(group_code="team_role", type=CONDITION, name="主力", value="")
```

`TemplateService.bind_rule` 在绑定过程中识别到混用时，返回 `{ "bound": true, "is_mixed_type": true }`，由前端弹确认框做软提示；service 同时打 warning 日志。后端不阻塞，业务合法。

**示例二：区间公式（劳动学分换算）**

注意：本设计区间为**半开半闭**：`input_min <= input < input_max`。所以 "0-60 学分" 应配置为 `input_min=0, input_max=61`；"61-100 学分" 应配置为 `input_min=61, input_max=null`。

```
template(name="劳动学分换算", category_id=劳动教育, max_score=10)
  └── rule(name="学分区间", type=TRANSFORM, score=NULL)            ← TRANSFORM 模式下 rule.score 必须为 NULL
        ├── attribute(group_code="credit", group_name="学分区间", type=TRANSFORM, name="0-60学分",   value="input * 0.5",           input_min=0,   input_max=61)
        └── attribute(group_code="credit", group_name="学分区间", type=TRANSFORM, name="61-100学分", value="30 + (input-60) * 0.3", input_min=61,  input_max=null)
```

**示例三：无范围公式（直接换算）**

```
template(name="GPA换算", category_id=学业加分, max_score=20)
  └── rule(name="GPA", type=TRANSFORM, score=NULL)                 ← 用户输入一个数值，按区间匹配 attribute 套公式
        └── attribute(group_code="gpa", group_name="GPA", type=TRANSFORM, name="GPA换算", value="input * 5", input_min=null, input_max=null)
```

### 3. Application（申请记录）

职责：记录学生的一次加分申请，包含快照数据、审批状态和操作日志。

共 3 张表：

---

#### applications（申请主表）

> **职责定位**：application 是**核心实体**，承载一次申请的 apply_score 快照和审批状态。proof 是挂在 application 下的辅助表（用于展示哪些证明通过 / 哪些被拒）；operation 是 application 的**审计日志**。三个表的写操作各司其职。

```sql
CREATE TABLE applications (
    id             SERIAL PRIMARY KEY,
    user_id        INTEGER NOT NULL REFERENCES users(id),
    template_id    INTEGER NOT NULL REFERENCES template(id),
    template_name  VARCHAR(100) NOT NULL,   -- 快照，防模板改名影响历史
    category_id    INTEGER NOT NULL REFERENCES template_category(id),  -- 冗余，便于聚合
    apply_score    DECIMAL(5,2) NOT NULL,   -- 由 template 计算得出，save_draft 时一次性快照，学生不能填写
    gain_score     DECIMAL(5,2) DEFAULT 0,  -- PASSED 时的 apply_score 快照（详见下方"gain_score 语义"）
    status         VARCHAR(20) DEFAULT 'DRAFT'
                   CHECK (status IN ('DRAFT','APPLYING','PASSED','REJECTED','CANCELLED','REVOKED')),
    review_count   INTEGER DEFAULT 1,       -- 从 template.review_count 快照，需不同审核员数
    approved_count INTEGER DEFAULT 0,       -- 已投赞成票的不同审核员数（SQL 原子 +1）
    rejected_count INTEGER DEFAULT 0,       -- 已投反对票的不同审核员数（SQL 原子 +1，配合 REJECT veto 语义）
    created_at     TIMESTAMP,
    updated_at     TIMESTAMP
);

-- 业务级唯一约束（不写 DB UNIQUE，由 service 层维护）：
--   同一用户对同一 template 只允许存在一条 status NOT IN ('REJECTED','CANCELLED','REVOKED') 的"活"申请
--   历史已 REJECTED / CANCELLED / REVOKED 的可以保留作为审计痕迹，不阻塞重新申请
CREATE INDEX idx_application_user   ON applications(user_id);
CREATE INDEX idx_application_status ON applications(status);
CREATE INDEX idx_application_user_template_status ON applications(user_id, template_id, status);
```

**gain_score 语义（v4.3 调整：随 proof 审核动态累加）：**

| 状态 | gain_score 取值 | 写入时机 |
|---|---|---|
| DRAFT | 0 | 创建时默认 0 |
| APPLYING（审核中） | 随审核实时变化 | 每次 `review_proof(APPROVED)` 原子 `+=proof_score`；`review_proof(REJECTED，前态为APPROVED)` 原子 `-=proof_score` |
| APPLYING（全部通过） | = `apply_score` | 所有 proof 均 APPROVED 后自然累计到位 |
| PASSED | = `apply_score`（不变） | pass_application 不再写 gain_score（已由 proof 审核过程维护到位） |
| REJECTED / CANCELLED / REVOKED | 当前累计值保留 | 不重置（可查历史审了多少） |

**status 流转（v4.3 采用 REJECT 一票否决语义）：**

```
                            ┌─学生取消──> CANCELLED（终态）
                            │
DRAFT ──提交──> APPLYING ──老师拒绝──> REJECTED ──学生重提──> APPLYING
        │              │     │
        │              │     └─ 老师拒绝（veto）→ status 立即 REJECTED
        │              │
        │              ├─老师通过 (approved_count == review_count)──> PASSED（终态）
        │              │
        │              └─学生取消──> CANCELLED（终态）
        │
        └─学生取消──> CANCELLED（终态）

老师撤回: PASSED ──老师撤回──> REVOKED（终态）
```

**各状态语义（v4.3）：**

| status | 终态？ | 学生操作 | 老师操作 |
|---|---|---|---|
| `DRAFT` | 否 | 编辑/提交/取消 | - |
| `APPLYING` | 否 | 取消 | 通过/拒绝 |
| `PASSED` | 是 | - | 撤回 |
| `REJECTED` | 否 | 修改proof/重提 | - |
| `CANCELLED` | 是 | - | - |
| `REVOKED` | 是 | - | - |

> 状态简洁明了：学生取消 → CANCELLED，老师拒绝 → REJECTED，老师撤回 → REVOKED。

**REJECT 的语义（一票否决 vs 多票过半）：**

本版采用 **REJECT 一票否决（veto）** 语义：

- 任意一个审核员点 REJECT（必须带 remark）→ application.status 立即 → REJECTED，其他审核员的 PASS 票作废
- 这与 `review_count >= 2` 多人审核的设计组合出"任一审核员能一票否决整个申请"的能力
- **理由**：学生误传材料的代价比"让一票否决更早暴露问题"高

> 注意：veto 语义下 `review_count` 的语义退化为"凑够赞成票数门槛"——只要凑够 N 个**不同**审核员的 PASS 票即 PASSED，任一 REJECT 立即打断。这与"少数服从多数"不同。前后端文案都要相应调整（"投票"一词会误导，应叫"会签"，"任意一票否决"）。

**关键规则（v4.3）：**

- `apply_score` 由计算引擎在 `save_draft` 时一次性算出并固化到 application；**学生不可填写，RESUBMIT 不可修改**。要改分数必须重新生成新申请（新建一条 DRAFT，不通过修改原 application）。
- **DRAFT 允许 0 proof**（草稿存在的核心理由：学生先存理论分，慢慢补证明）。submit 时校验 `len(proofs) >= 1` 且 `sum(proof.proof_score) == apply_score`（DECIMAL 精度对齐，差 0.01 都不行）。
- **提交与再提交**（submit / resubmit）必须严格校验：≥ 1 proof + sum == apply_score。submit 与 resubmit 的校验逻辑**完全同构**——resubmit 不需要 `delete_proof_ids` / `new_proof_data_list` 字段，统一走"整体替换 proof 列表"。
- 审核员 PASS 前**业务层校验**（service 层实时查 proof 表）：该 application 下所有 proof 均为 APPROVED。
- 第 `review_count` 个**不同审核员**的 PASS（CAS 原子 `approved_count = approved_count + 1`，达到 review_count）→ status → PASSED → 同一事务内写 ScoreData。
- 任意审核员点 REJECT（**remark 必填**）→ status 立即变为 REJECTED（veto，已投的 PASS 票作废但不撤回 operation 记录）。
- **同审核员对同 application 只能投 1 次**（PASS 或 REJECT 都算一次），由 service 层在写入 operation 前查 `(application_id, operator_id)` 在 operation 表上有没有 PASS/REJECT 记录。
- `template_name` / `review_count` / `operator_name` 均为快照，防止源数据变更影响历史。
- application 本身**不再存储 remark / reviewer_ids / review_records 字段**——所有这些信息都从 `application_operation` 查询得出（避免 JSONB 读-改-写的并发丢失）。
- proof 上**也不再存 remark**——审核员对 proof 的 REJECTED 决定就是改 `application_proofs.status = 'REJECTED'`，不写 operation（proof 不是核心审计对象）。

#### application_proofs（证明材料）

> **职责定位**：proof 是 application 下的**辅助展示表**，记录学生上传的每份证明材料 + 对应分值 + 当前审核状态。proof 不是核心审计对象——审核员对 proof 的决定只通过 `application_proofs.status` 字段表达，不写入 application_operation。

```sql
CREATE TABLE application_proofs (
    id             SERIAL PRIMARY KEY,
    application_id INTEGER NOT NULL REFERENCES applications(id) ON DELETE CASCADE,
    file_id        INTEGER REFERENCES file_metadata(id),    -- 可空：学生可填"文字承诺"等无文件证明；非空时定位到 file_metadata 即可读到 S3 object_name
    proof_score    DECIMAL(5,2) NOT NULL CHECK (proof_score >= 0),
    status         VARCHAR(20) DEFAULT 'PENDING'
                   CHECK (status IN ('PENDING','APPROVED','REJECTED')),
    created_at     TIMESTAMP,
    updated_at     TIMESTAMP
);

CREATE INDEX idx_proofs_application ON application_proofs(application_id);
CREATE INDEX idx_proofs_status      ON application_proofs(application_id, status);
```

**关键约束（v4.2 收紧）：**

- proof **草稿阶段允许 0 条**（学生可以先存理论分，再慢慢补证明）
- **submit / resubmit 时**校验：`len(proofs) >= 1` 且 `sum(proof_score) == apply_score`（DECIMAL 精度对齐，差 0.01 都不行）
- `proof_score` 为非负 DECIMAL（DB 层 CHECK）
- `file_id` nullable：允许文字描述 / 承诺书等无文件证明；非空时通过 file_metadata 定位到 S3 object_name（无需单独存 URL，路由层根据 file_id 拼预签名 URL）

**proof 的状态机（**仅用于展示**，不约束学生操作）：**

```
PENDING ←──────────────┐  ← 学生 RESUBMIT 重传
   │                    │
   ├─ APPROVED ─────────┤
   │                    │
   └─ REJECTED ─────────┤
                        │
       RESUBMIT 全集合替换 ─→ 学生重新编辑可改任意 proof.status
```

- 审核员逐条标记 proof APPROVED / REJECTED（**仅改 `application_proofs.status`，不写 application_operation**）
- proof.status 是 application 投 PASS 的**前置校验条件**：当 application 下**所有 proof.status == APPROVED** 时 → 审核员方可点击 application 整体 PASS（service 层实时查表）
- proof.status 是会签过程的中间状态，**任意审核员都可以修改**——后到的审核员覆盖前到的决定（详见下方"proof 的会签覆盖语义"）
- proof REJECTED 时**不需要** remark 必填——审核员如果想说明理由，鼓励写 remark，但 service 不强制

**审核员对 proof 的并发约束（v4.2 重写）：**

| 场景 | 行为 |
|---|---|
| 不同审核员并发审 application 的不同 proof | 互不干扰（行级锁隔离） |
| 不同审核员并发审 application 的**同一 proof** | service 层 `SELECT ... FOR UPDATE` 串行化，**后到的覆盖前到的 status**（veto 视角的"实质性反对"） |
| 同一审核员对 application 的同一 proof 重复请求 | 409 Conflict（同一个审核员不能重复表达决定；不同审核员可以互相覆盖） |

**关键业务流程（review_count 区分）：**

**`review_count = 1`（单人审核，单步通过）：**

```
审核员 A: 审完全部 proof（全部 APPROVED）→ 投 PASS application
  └─ approved_count = 1 == review_count → application.status → PASSED
  └─ 同一事务：gain_score = apply_score + 写 score_data
  └─ application.status = PASSED 是终态
```

如果发现 application 有问题，必须走 REVOKE 撤销流程（v4.2 仅结构预留，本期不实现）。

**`review_count ≥ 2`（多人会签 + veto）：**

```
审核员 A: 审完全部 proof（全部 APPROVED）→ 投 PASS application
  └─ approved_count = 1, application.status 仍为 APPLYING
  └─ 不写 ScoreData（还没到 review_count）

审核员 B: 审 application 时认为 proof X 有问题
  ├─ 路径 1：B 把 proof X 从 APPROVED 改成 REJECTED
  │   └─ 此时所有 proof 不全 APPROVED，B 投 PASS application 必然失败
  │   └─ B 必须改投 application REJECTED → status → REJECTED（veto）
  ├─ 路径 2：B 直接投 application REJECTED（不管 proof 状态）
  │   └─ application.status → REJECTED，proof 状态保留

关键不变量：
  - proof.status 是 application 投 PASS 的**前置校验条件**——COUNT(proof.status='PENDING' OR 'REJECTED') == 0 才能 PASS
  - proof.status 改变**不会自动触发** application.status 变化——B 改完 proof 后必须主动投 application
  - PASSED 之后 proof 不能再改（review_proof 在 PASSED 状态返回 409 Conflict）
```

**REJECTED 后修改规则（v4.2 放开）：**

- 学生可在 RESUBMIT 时**对任意 proof 增删改**（不只是 REJECTED 的 proof，APPROVED 的也能改）
- 学生侧对 proof 的修改只发生在 RESUBMIT（REJECTED 状态）；APPLYING 状态下学生侧 proof 锁定
- 重新提交（RESUBMIT）后 `application.status → APPLYING`，**所有 proof 状态统一重置为 PENDING**（待新一轮审核）
- RESUBMIT 时校验：≥ 1 proof 且 sum(proof.proof_score) == apply_score，与 submit 完全同构
- **submit 与 resubmit 的 service 接口完全对称**——前端不需要为 RESUBMIT 单独设计"删除哪些 proof / 新增哪些 proof"的 diff，复用相同的"提交整个 proof 列表"逻辑

**proof 的整体替换语义：**

service 层在 `submit` / `resubmit` 时**不需要精细化的 delete_proof_ids + new_proof_data_list 字段**——前端直接提交完整的 proof 列表，service 层做整体替换：

```python
# submit / resubmit 的 proof 处理逻辑（共 4 行）
old_ids = SELECT id FROM application_proofs WHERE application_id = ?
DELETE FROM application_proofs WHERE application_id = ? AND id IN (old_ids)
for proof in proof_list:
    INSERT INTO application_proofs (application_id, file_id, proof_score, status) VALUES (?, ?, ?, 'PENDING')
```

不需要区分"哪些 proof 是新增 / 哪些是删除 / 哪些是保留"，因为 **submit 时所有 proof 都要被审核员从头审**，旧的"已审过"状态没有意义。

#### application_operation（application 操作日志，v4.3 简化版）

职责：application **级别的**只追加审计日志，记录 application 自身的状态迁移操作。**proof 状态变更不记入此表**——proof.status 在 application_proofs 表里表达。

v4.3 简化：operation 字段改为存储操作后的 application.status，不再使用 ApplicationOperationType 枚举。

```sql
CREATE TABLE application_operation (
    id               SERIAL PRIMARY KEY,
    application_id   INTEGER NOT NULL REFERENCES applications(id),
    operator_id      INTEGER NOT NULL,
    operator_name    VARCHAR(100) NOT NULL,  -- 快照操作人姓名（审核员可能离职）
    status          VARCHAR(20)  NOT NULL    -- 操作后 application 的状态
                     CHECK (status IN ('DRAFT', 'APPLYING', 'PASSED', 'REJECTED', 'CANCELLED', 'REVOKED')),
    remark           TEXT,                   -- 拒绝/撤回时必填，其他可选
    created_at       TIMESTAMP DEFAULT NOW()  -- 无 updated_at，操作记录不可修改
);

CREATE INDEX idx_operation_application ON application_operation(application_id);
CREATE INDEX idx_operation_created_at  ON application_operation(created_at);
CREATE INDEX idx_operation_app_status ON application_operation(application_id, status);
```

**操作与状态映射（v4.3）：**

| 操作 | 触发者 | operation.status 值 |
|---|---|---|
| 创建草稿 | 学生 | `DRAFT` |
| 取消草稿 | 学生 | `CANCELLED` |
| 提交申请 | 学生 | `APPLYING` |
| 取消申请 | 学生 | `CANCELLED` |
| 重提申请 | 学生 | `APPLYING` |
| 通过申请 | 老师 | `PASSED` |
| 拒绝申请 | 老师 | `REJECTED` |
| 撤回申请 | 老师 | `REVOKED` |

> 谁操作的由业务逻辑隐含：学生操作 → CANCELLED/APPLYING，老师操作 → REJECTED/PASSED/REVOKED。

**操作日志示例（v4.3）：**

```
operator    | status      | remark
张三(学生) | DRAFT       | NULL                        ← 学生在 template 详情页点了"生成申请草稿"
张三(学生) | APPLYING    | NULL                        ← 学生补充完 proof，点"提交"
李老师     | PASSED      | "其余材料均符合要求"          ← 第一票
王老师     | PASSED      | NULL                        ← 第二票，approved_count=2=review_count → PASSED
李老师     | REJECTED    | "国家级证书编号无法在系统中检索"  ← REJECT（veto），前两票作废
张三(学生) | APPLYING    | NULL                        ← 学生修改 proof 后重提
王老师     | REJECTED    | "材料不清晰"                  ← 又一个 REJECT
张三(学生) | CANCELLED   | "不想要了"                    ← 学生主动取消
李老师     | REVOKED     | "发现造假"                    ← 老师撤回已通过的申请
```

> **设计取舍**：
> - 把"application 状态迁移"作为操作日志的核心：SUBMIT / PASS / REJECT / RESUBMIT / WITHDRAW / DISCARD_DRAFT 都是 application 层面有意义的"事件"
> - 把"学生编辑草稿"排除出去（噪声大 / 不是事件 / 没有 state 变化）——CREATE_DRAFT 保留是给"申请诞生"留个 trace
> - 把"审核员审 proof"排除出去（proof 是辅助表，proof.status 字段就是审计介质）
> - WITHDRAW 是 APPLYING 阶段的合法出口，给学生"撤回重写"的机会（比"等审核员 REJECT"更主动）
> - REVOKE 暂不实现，但 CHECK 已包含，避免后续 schema 迁移

**关键设计（v4.2）：**

- `apply_score` 由计算引擎在 save_draft 时算出并快照，**学生不可填写，RESUBMIT 不可修改**
- `gain_score` 在 PASSED 时一次性写为 `apply_score`（不再是 proof 逐条累加）
- `approved_count` / `rejected_count` 用 SQL 算术表达式原子更新，禁止 ORM 读-改-写
- `template_name` / `review_count` / `operator_name` 均为快照，防止源数据变更影响历史
- DRAFT 状态的"保存草稿"不记录 operation（噪音太大），CREATE_DRAFT 是申请**诞生**的事件，记录一次
- operation 表**不带 target_id / target_type**——所有 operation 都是 application 级别的，proof 状态变更不在此记录
- application 表本身**不存 remark / reviewer_ids / review_records 字段**——所有这些信息从 `application_operation` 查询得出（避免 JSONB 读-改-写的并发丢失）
- proof **不带 reviewed_by / reviewed_at**——proof 是辅助表，proof.status 是审核员决定的事实来源
- proof 状态变更（APPROVED/REJECTED）**不写 application_operation**——审核员对 application 的 PASS 是 application 层面的事件；proof.status 只在 application_proofs 表里查

#### 审核员协作模型（v4.2 业务场景）

`review_count` 字段控制审核员协作人数，业务上分两种场景：

**场景 A：`review_count = 1`（单人审核，单步通过）**

这是**最常见**的场景——一个审核员看完所有 proof + application 直接 PASSED：

```
[1] 学生提交 → application.status = APPLYING
[2] 审核员 A：审 proof 1 (PENDING → APPROVED)
[3] 审核员 A：审 proof 2 (PENDING → APPROVED)
...（所有 proof APPROVED）
[N] 审核员 A：投 PASS application
        └─ approved_count = 1 == review_count → 触发 PASSED
        └─ 同事务：gain_score = apply_score + 写 score_data
        └─ application.status = PASSED（终态）
```

如果发现 application 有问题，必须走 REVOKE 撤销流程（v4.2 仅结构预留，本期不实现）。

**场景 B：`review_count ≥ 2`（多人会签 + 一票否决）**

每个审核员都可以修改任何 proof 的 status（包括覆盖前一个审核员的决定）：

```
[1] 学生提交 → application.status = APPLYING

[2] 审核员 A：审 proof 1 (PENDING → APPROVED)
[3] 审核员 A：审 proof 2 (PENDING → APPROVED)
[4] 审核员 A：投 PASS application
        └─ approved_count = 1, status 仍为 APPLYING
        └─ 不写 ScoreData（还没到 review_count）

[5] 审核员 B：审 proof 1 (APPROVED → REJECTED)  ← 覆盖 A 的决定
        └─ proof 1 的 status 是会签中间状态，B 可以表达实质性反对
[6] 审核员 B：试图投 PASS application
        └─ service 校验 COUNT(proof.status='PENDING' OR 'REJECTED') == 0
        └─ 失败：proof 1 是 REJECTED → 409 Conflict "还有 N 份证明未通过"
[7] 审核员 B：改投 REJECT application（veto）
        └─ application.status = REJECTED
        └─ 之前 A 投的 PASS 操作保留在 application_operation 历史中
        └─ proof 状态保留（A 的 APPROVED 被 B 改成 REJECTED）
```

**关键不变量**：

1. **proof.status 是会签中间状态**，不是终态——任意审核员可以修改（包括覆盖）
2. **proof.status 改变不会自动触发 application.status 变化**——B 改完 proof 后必须主动投 application
3. **PASSED 是 proof 和 application 的双重终态**——PASSED 之后 proof 不能再改（review_proof 返回 409）
4. **gain_score 是 application 整体通过的快照**——proof.status 变化不影响 gain_score，gain_score 只在 PASSED 时一次性写入

**为什么不需要 proof.review_count / proof.approved_count**：

- proof 的"是否通过"由 **最后一个审它的审核员** 决定，不是 N 个审核员的累计
- B 投 REJECTED 就是把 A 的 APPROVED 覆盖——这是 veto 视角下的业务表达
- 如果想看"这条证明被几个审核员审过、怎么决定的"——查 application_operation（虽然 v4.2 不写 REVIEW_PROOF，但 application 的 PASS/REJECT 操作日志能看到投票过程）
- 真正的"多人确认"在 application 层面（approved_count）实现，不是 proof 层面

#### 审核员投票模型与并发约束

application 自身不存"哪些审核员投过票"的字段——全部从 `application_operation` 倒推。本节明确这背后的并发约束与幂等性。

**1. 同一审核员重复投票的约束（v4.2 强调"不同审核员累计"语义）：**

| 场景 | 行为 |
|---|---|
| 同一审核员对同一 application 重复 PASS | 第二次请求返回 409 Conflict（已投过票），**approved_count 不增** |
| 同一审核员对同一 application 重复 REJECT | 第二次请求返回 409 Conflict（已投过票），**veto 已生效，无副作用** |
| 同一审核员对同一 proof 重复审 | 第二次请求返回 409 Conflict（proof.status 已被改过） |
| **不同**审核员对 application 各自 PASS | 第 1 个 PASS → approved_count=1；第 2 个 PASS → approved_count=2 = review_count → status = PASSED |

> **v4.2 关键决策**：`review_count = N` 语义为"N 个**不同**审核员各投 1 票 PASS"。v4.1 把这个写成"凑够赞成票数"含糊，本期明确：如果业务希望"单审核员反复审不算"，就靠"同审核员去重"机制保证——一个审核员只能投 1 票。

**实现：**

`pass_application` 在写入 `operation='PASS'` 前，先 SELECT 该 (application_id, operator_id) 是否已存在 PASS / REJECT 操作：

```sql
SELECT EXISTS (
    SELECT 1 FROM application_operation
    WHERE application_id = ? AND operator_id = ?
      AND operation IN ('PASS', 'REJECT')
)
-- 存在则拒绝，不写 operation、不增 approved_count
```

`review_proof` 的幂等通过 service 层校验实现（v4.2 移除 reviewed_by 字段）：
- **同审核员不能重复审**：service 层校验 (proof_id, reviewer_id) 没有审过这条 proof——重复请求返回 409 Conflict
- **不同审核员可以覆盖**：UPDATE proof SET status=? 不带 AND status='PENDING' 条件——B 审核员可以把 A 审核员的 APPROVED 改成 REJECTED（veto 视角）
- proof 状态变更只发生在 application.status == 'APPLYING' 阶段（PASSED 是双重终态，PASSED 之后 review_proof 返回 409）

**2. 不同审核员并发审核的约束：**

- **不同审核员审不同 proof**：完全独立，无需额外锁（行级锁隔离）
- **不同审核员审同一 proof**：service 层 `SELECT ... FOR UPDATE` 串行化，先到先得，后到者发现 status 已非 PENDING → 409
- **不同审核员对 application 投票 PASS/REJECT**：
  - REJECT 必胜——一旦任一审核员 REJECT，application.status → REJECTED，service 端 `pass_application` 前置条件检查 `status == 'APPLYING'` 失败，**后到的 PASS 全部拒绝**
  - 这是"任一 REJECT 立即驳回"语义的关键技术实现
- **第 N 个 PASS 触发 PASSED**：`approved_count + 1 == review_count` → 同事务内写 ScoreData（pass_application 内）

**3. 关键 SQL 模式（必须在文档里固化）：**

```sql
-- 投票通过：先校验幂等，再 CAS 检查 status，原子增 approved_count
UPDATE applications
SET approved_count = approved_count + 1
WHERE id = ? AND status = 'APPLYING'
RETURNING approved_count, review_count, status;
-- service 层判断：
--   if returned.status != 'APPLYING' -> 该 application 已被 REJECT 或 WITHDRAW，拒绝本次 PASS
--   if approved_count == review_count ->
--       UPDATE applications SET gain_score = apply_score, status = 'PASSED' WHERE id = ? AND status = 'APPLYING'
--       ScoreDataService.record(db, user_id, application_id, category_id, name, apply_score) ← 同一事务

-- 一票否决：CAS 翻 status
UPDATE applications
SET status = 'REJECTED', rejected_count = rejected_count + 1
WHERE id = ? AND status = 'APPLYING'
RETURNING id;
-- 拿到结果后写 application_operation(operation='REJECT') + 后续 RESUBMIT 准备
```

**禁止的反模式：**

- ❌ ORM 读取 approved_count → Python +1 → UPDATE SET approved_count = ?（并发下两个审核员同时 +1 但只写一次 → 丢票）
- ❌ ORM 读取 status → if APPLYING → UPDATE SET status = 'PASSED'（并发下两个审核员都判定通过 → 重复状态写）
- ❌ ORM 读取 proof.status → 全部 PENDING → PASS application（proof 在审核员投票间隙被学生改了状态，需要 service 层**事务内 SELECT FOR UPDATE 防幻读**）

**4. application 的"已投票"信息查询：**

管理端 / 学生端要展示"谁投了票、什么时候投的"，全部从 application_operation 查询：

```sql
SELECT operator_id, operator_name, operation, remark, created_at
FROM application_operation
WHERE application_id = ? AND operation IN ('PASS', 'REJECT')
ORDER BY created_at ASC;
```

`approved_count` / `rejected_count` 字段是冗余缓存（方便 WHERE 子句快速判断"是否已 PASSED"），但**事实来源始终是 application_operation**。

**5. 投票后被 REJECT veto 的历史处理：**

假设 A、B、C 三个审核员，A、B 已投 PASS（approved_count=2, review_count=3），C 投 REJECT：

- application.status 立即变 REJECTED
- application_operation 中保留 A、B 的 PASS 记录、C 的 REJECT 记录（**不撤回**）
- 业务上"已投的票"作为历史保留，学生 RESUBMIT 后再走一遍
- **新投票不累加**到旧 approved_count 上——RESUBMIT 后 approved_count 不重置（依然是 2），而是继续累加到 3

> ⚠️ **spec 决策**：approved_count **不重置**（保留历史投票）。如果业务希望 RESUBMIT 后"重新会签"，把 approved_count 在 RESUBMIT 时重置为 0。本期**保留历史**，与 WITHDRAW 后允许重新申请互不冲突（这两件事是不同维度的）。

### 4. ScoreData（流水记录）

职责：记录每条申请通过（`application.status → PASSED`）后的得分，作为聚合计算的原始数据，追加只写。

```sql
CREATE TABLE score_data (
    id             SERIAL PRIMARY KEY,
    user_id        INTEGER NOT NULL REFERENCES users(id),
    application_id INTEGER NOT NULL REFERENCES applications(id),
    category_id    INTEGER NOT NULL REFERENCES template_category(id),  -- 叶子节点
    name           VARCHAR(100),            -- 模板名快照，展示用
    score          DECIMAL(5,2) NOT NULL,   -- application.apply_score 快照（v4.2：与 gain_score 数值相同，语义取 apply_score 更直观）
    is_active      BOOLEAN DEFAULT TRUE,    -- FALSE = 该申请被外部标记为失效，recalculate 时排除
    created_at     TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_score_data_user_active ON score_data(user_id, is_active);
```

**写入时机：** `application.status → PASSED` 时由 `ApplicationService.pass_application()` 在同一事务内调用 `ScoreDataService.record()` 写入一条（approved_count 达到 review_count 时触发）。

**失效处理（is_active=FALSE）：** 未来如果增加"撤销已通过申请"的扩展能力，将对应 `score_data.is_active = FALSE`，下次 `recalculate` 自动排除，`user.score_info` 自然更新。本期**不实现该流程**。

**聚合算法（自底向上树遍历）：**

```
Step 1：SQL 聚合叶子分类原始分
  SELECT category_id, SUM(score)
  FROM score_data
  WHERE user_id = ? AND is_active = TRUE
  GROUP BY category_id

Step 2：内存中组装 template_category 树（一次全表查询，按 parent_id 建树）

Step 3：后序递归，自底向上封顶
  叶子节点：capped = min(SUM(score), category.max_score)
  非叶节点：capped = min(sum(子节点 capped), category.max_score)

Step 4：覆盖写入 user.score_info（幂等，可反复触发）
```

> template.max_score 已在 calculate 阶段完成独立封顶（写入 score_data 的 score 已经 ≤ template.max_score），此处分类封顶是上一层级的自然封顶。

**算法示例（4 层树）：**

```
总分(max=100)
  └── 加分(max=80)
        ├── 学业(max=60)：竞赛raw=25→capped=20，论文raw=15→capped=10，学业capped=min(30,60)=30
        └── 专长(max=30)：体育raw=35→capped=30，专长capped=min(30,30)=30
加分capped = min(30+30, 80) = 60
总分capped = min(60, 100) = 60
```

```python
# 依赖：pip install simpleeval（安全的数学公式解析，禁止任意代码执行）
from simpleeval import simple_eval

class ScoreCalculationService:

    @staticmethod
    def calculate(template, user_selections: dict) -> float:
        """
        遍历 template 的所有 rule，按 rule.sort_order 顺序处理：
        user_selections 结构：
          { rule_id: attribute_id }     # CONDITION 规则：用户选中的 attribute id
          { rule_id: "75.0" }           # TRANSFORM 规则：用户输入的数值字符串
        返回封顶后的分数（min(total, template.max_score)）。

        template.rules 已通过 selectinload 预加载，1 次 SQL 拿到全部数据（无 N+1）。
        """
        total = 0.0
        for rule in sorted(template.rules, key=lambda r: r.sort_order):
            selected = user_selections.get(rule.id)
            if selected is None:
                continue  # 未填写的 rule 不参与计分

            # rule 内的 attribute 排序统一按 attribute.sort_order
            attrs = sorted(rule.attributes, key=lambda a: a.sort_order)
            if not attrs:
                continue

            if attrs[0].type == "CONDITION":
                # CONDITION 模式：用户选 attribute，加 rule.score（不管选哪个都一样）
                if any(selected == a.id for a in attrs):
                    if rule.score is None:
                        raise ValueError(f"rule={rule.id} 含 CONDITION attribute 但 score=None")
                    total += float(rule.score)
            else:
                # TRANSFORM 模式：用户输入数值，按半开半闭区间 [min, max) 匹配 attribute
                user_input = float(selected)
                matched = False
                for attr in attrs:
                    if attr.input_min is not None and user_input < float(attr.input_min):
                        continue
                    if attr.input_max is not None and user_input >= float(attr.input_max):
                        continue
                    # 使用 simpleeval 替代 eval，禁止任意代码执行
                    total += simple_eval(attr.value, names={"input": user_input})
                    matched = True
                    break
                if not matched:
                    raise ValueError(
                        f"user_input={user_input} 不在 rule={rule.id} 的任何 attribute 区间内"
                    )

        return min(total, float(template.max_score))
```

### Layer 3：ApplicationService

```python
class ApplicationService:

    @staticmethod
    async def save_draft(db, user_id: int, template_id: int,
                         user_selections: dict, proof_data_list: list) -> Application:
        """
        创建或覆盖更新草稿（DRAFT，**允许 0 proof**），本期不写 application_operation：
        1. 业务级唯一约束：同 (user_id, template_id) 不允许有另一条 status IN ('DRAFT','APPLYING','PASSED') 的活申请
           - 已有 DRAFT → 覆盖式更新（保留 application.id，复用 proof 集合结构）
           - 已有 APPLYING / PASSED → 拒绝（必须先取消或者走撤销流程）
           - 历史已有 REJECTED / CANCELLED / REVOKED → 允许新建草稿（互不阻塞）
        2. 调用 ScoreCalculationService.calculate() 算出 apply_score（前端实时算的同一份公式，服务端权威）
        3. 创建/更新 Application：status='DRAFT'，apply_score 快照，template_name/review_count/template_id 从 template 拷贝
        4. **整体替换 proof 集合**：
           - DELETE FROM application_proofs WHERE application_id = ?
           - INSERT new proof rows（status='PENDING', file_id nullable）
           - proof 列表允许为空（草稿阶段可暂存理论分）
        5. DRAFT 不强校验 sum 守恒（前端展示差额）
        6. INSERT application_operation(status='DRAFT') 记录申请诞生
        返回 Application（含已加载的 proofs）
        """

    @staticmethod
    async def cancel(db, application_id: int, user_id: int,
                     remark: Optional[str] = None) -> Application:

        学生主动取消申请（DRAFT/APPLYING → CANCELLED，终态）：
        1. 校验 application.user_id == user_id（仅本人可取消）
        2. 校验 status IN ('DRAFT', 'APPLYING')
        3. 同一事务：
           - UPDATE application SET status = 'CANCELLED'
           - INSERT application_operation(status='CANCELLED', remark=optional)
        不物理删除 application 行（保留审计痕迹）

        前置条件（全部满足，否则 409 / 400）：
          1. application.user_id == user_id（仅本人）
          2. application.status == 'DRAFT'  ← REJECTED 必须走 resubmit
          3. len(proofs) >= 1  ← 草稿允许 0 proof，但提交时必须 ≥ 1
          4. sum(proof.proof_score) == apply_score（DECIMAL 精度对齐，差 0.01 都不行）
        同一事务：
          - 整体替换 proof 集合（先 DELETE 旧 proof，再 INSERT 新 proof，**status 全部置 PENDING**）
          - UPDATE applications SET status = 'APPLYING' WHERE id = ? AND status = 'DRAFT'
          - INSERT application_operation(status='APPLYING')
        注：REJECTED 状态的提交走 resubmit()。spec 不允许 submit() 处理 REJECTED。
        """

    @staticmethod
    async def withdraw(db, application_id: int, user_id: int,
                       remark: Optional[str] = None) -> Application:
        """
        学生主动撤回（APPLYING → CANCELLED，终态）：
        前置条件：
          1. application.user_id == user_id（仅本人可撤）
          2. application.status == 'APPLYING'  ← 仅 APPLYING 可撤回
        业务动机：学生提交后发现填错，不必等审核员 REJECT，主动撤回为终态后再开新草稿
        同一事务：
          - UPDATE application SET status = 'CANCELLED'
          - INSERT application_operation(status='CANCELLED', remark=optional)
          - 不动 proof 集合（保留审计）
        """

    @staticmethod
    async def review_proof(db, proof_id: int, reviewer_id: int,
                           action: str, remark: Optional[str] = None) -> ApplicationProof:
        """
        审核员对单条 proof 做出 APPROVED / REJECTED 决定（**不写 application_operation**）：

        v4.2 决策：proof.status 是会签中间状态，**任意审核员都可以修改**——
                  后到的审核员覆盖前到的决定（veto 视角的实质性反对）。
                  proof 不需要 review_count / approved_count 字段。

        前置条件：
          1. proof.application_id 对应的 application.status == 'APPLYING'
             ← PASSED 之后 proof 不能再改（veto 只能在 APPLYING 阶段生效）
          2. **同审核员去重**：该 reviewer_id 没有审过这条 proof（不允许重复表达决定）
             但不同审核员可以互相覆盖
          3. action == 'APPROVED' or 'REJECTED'（不需要 remark 必填，service 层不强制）

        同一事务：
          - SELECT proof JOIN application FOR UPDATE
          - 校验 application.status == 'APPLYING'
          - 校验 reviewer_id 没审过该 proof（查 application_operation 不必要——
            可以直接在 proof 表加 reviewer_id 记录，但 v4.2 spec 选择在 service 层查询历史）
          - UPDATE application_proofs SET status = ?
            不带 AND status='PENDING' 条件——**允许覆盖任意已有状态**
        副作用：**不更新 application.gain_score**（v4.2 决策——gain_score 在 PASSED 时一次写）
        也不写 application_operation（proof 是辅助表）

        返回更新后的 proof
        错误码：
          - application 状态非 APPLYING → 409 Conflict
          - 同一 reviewer_id 重复审 → 409 Conflict（不允许同审核员重复表达决定）
          - 任意不同 reviewer_id 覆盖 → 允许（这就是 veto 的业务表达）
        """

    @staticmethod
    async def pass_application(db, application_id: int, reviewer_id: int,
                               reviewer_name: str,
                               remark: Optional[str] = None) -> Application:
        """
        审核员投票通过 application：

        前置条件（全部满足）：
          1. application.status == 'APPLYING'  ← 被 REJECT veto 后这条直接拒绝
          2. 该 application 下 **所有 proof.status == 'APPROVED'**
          3. (application_id, reviewer_id) 在 application_operation 上 status IN ('PASSED','REJECTED') 不存在

        同一事务：
          a. SELECT ... FOR UPDATE 锁住 application 行
          b. UPDATE applications SET approved_count = approved_count + 1 WHERE id = ? AND status = 'APPLYING'
             -- 如 affected_rows = 0 → 状态已变（被 REJECT veto 或被学生 WITHDRAW），拒绝
          c. 若 approved_count == review_count：
             UPDATE applications SET status = 'PASSED' WHERE id = ? AND status = 'APPLYING'
             ScoreDataService.record(db, user_id, application_id, category_id, name, apply_score)
          d. INSERT application_operation(status='PASSED', operator_id, operator_name, remark)
        错误码：
          - 状态非 APPLYING → 409 Conflict
          - 还有 PENDING 或 REJECTED proof → 409 Conflict（前端提示"还有 N 份证明未通过"）
          - 该审核员已投过票 → 409 Conflict
        """

    @staticmethod
    async def reject_application(db, application_id: int, reviewer_id: int,
                                 reviewer_name: str, remark: str) -> Application:
        """
        审核员一票否决 application（veto 语义）：
        前置条件：
          1. application.status == 'APPLYING'
          2. remark 非空字符串（service 层校验 trim 后非空，否则 400）
          3. (application_id, reviewer_id) 在 application_operation 上没有记录

        同一事务：
          a. SELECT ... FOR UPDATE 锁住 application 行
          b. UPDATE applications SET status = 'REJECTED', rejected_count = rejected_count + 1
             WHERE id = ? AND status = 'APPLYING'
             -- 如 affected_rows = 0 → 状态已变，拒绝
          c. INSERT application_operation(status='REJECTED', operator_id, operator_name, remark=必填)
        错误码：
          - 状态非 APPLYING → 409 Conflict
          - remark 为空 → 400
          - 该审核员已投过票 → 409 Conflict
        """

    @staticmethod
    async def resubmit(db, application_id: int, user_id: int,
                       proof_data_list: list) -> Application:
        """
        学生修改 proof 后重新提交（REJECTED → APPLYING）：
        **与 submit 完全同构**——不复用 delete_proof_ids/new_proof_data_list 字段，统一走"整体替换 proof 列表"。

        前置条件（全部满足）：
          1. application.user_id == user_id（仅本人可 resubmit）
          2. application.status == 'REJECTED'  ← 仅 REJECTED 可走 resubmit
          3. len(proof_data_list) >= 1
          4. sum(p.proof_score for p in proof_data_list) == apply_score（DECIMAL 精度对齐）

        同一事务：
          a. SELECT ... FOR UPDATE 锁住 application 行
          b. DELETE FROM application_proofs WHERE application_id = ?
          c. INSERT proof_data_list 中所有 proof（status='PENDING'，file_id nullable）
          d. UPDATE applications SET status = 'APPLYING' WHERE id = ? AND status = 'REJECTED'
          e. INSERT application_operation(status='APPLYING')

        错误码：
          - 状态非 REJECTED → 409 Conflict
          - sum 不守恒 / proof 数量为 0 → 400
        """

    @staticmethod
    async def revoke_application(db, application_id: int, reviewer_id: int,
                                reviewer_name: str, remark: str) -> Application:
        """
        老师撤回已通过的申请（PASSED → REVOKED，终态）：
        前置条件：
          1. application.status == 'PASSED'
          2. remark 非空字符串
        同一事务：
          a. SELECT ... FOR UPDATE 锁住 application 行
          b. UPDATE applications SET status = 'REVOKED' WHERE id = ? AND status = 'PASSED'
          c. INSERT application_operation(status='REVOKED', operator_id, operator_name, remark=必填)
        错误码：
          - 状态非 PASSED → 409 Conflict
          - remark 为空 → 400
        """


class ApplicationOperationService:
    """
    application_operation 的查询服务（用于审计 / 详情页）：
    所有 application 上的操作历史都从这里查询。
    """

    @staticmethod
    async def list_by_application(db, application_id) -> list[ApplicationOperation]:
        """返回 application 的全部操作历史，按 created_at ASC"""

    @staticmethod
    async def list_votes(db, application_id) -> list[ApplicationOperation]:
        """返回所有投票记录（status IN ('PASSED','REJECTED')），用于详情页展示"""

    @staticmethod
    async def has_voted(db, application_id, operator_id) -> bool:
        """判断 (application_id, operator_id) 是否已投过票（PASSED 或 REJECTED）"""
```

### Layer 4：ScoreDataService（v4.2 重构——解耦 application 与 recalculate）

```python
class ScoreDataService:

    @staticmethod
    async def record(db, user_id: int, application_id: int,
                     category_id: int, name: str, score):
        """
        写入流水记录，由 ApplicationService.pass_application() 在**同一事务**内调用：
          - score = application.apply_score 快照（不是 gain_score，避免双字段冗余）
          - is_active = TRUE
        本期不调 recalculate——recalculate 是独立接口，按需触发。
        """

    @staticmethod
    async def recalculate(db, user_id: int) -> dict:
        """
        全量聚合 + 覆盖写 user.score_info，幂等可反复触发：

        1. SELECT score_data WHERE user_id=? AND is_active=TRUE，按 category_id GROUP BY SUM(score)
        2. SELECT * FROM template_category，内存中按 parent_id 组装树
        3. 后序递归：叶子 capped = min(raw, max_score)；非叶 capped = min(子节点之和, max_score)
        4. 收集所有节点得分，覆盖写入 user.score_info
        5. 返回 user.score_info 字典
        （仅需 2 次 SELECT + 1 次 UPDATE，全程内存递归）

        本期由"学生点击刷新成绩"或"管理员手动触发"调用，**不与 application.pass_application 同步触发**。
        """

    @staticmethod
    async def get_summary(db, user_id: int) -> dict:
        """读取 user.score_info 快照，不重算，供前端直接展示"""
```

**recalculate 触发策略（v4.2 决策：解耦到独立接口）：**

v4.2 **撤销 v4.1 的同步触发设计**——application.pass_application 只写 score_data.row，**不触发** recalculate。职责切分：

| 入口 | 责任 |
|---|---|
| `ApplicationService.pass_application` | 写 score_data 行 + 翻 application.status=PASSED |
| `ScoreDataService.recalculate` | 聚合 score_data + 写 user.score_info |

**为什么解耦：**

- ✅ 单一职责：application 不依赖 score_data 写入是否成功，也不依赖 user.score_info 是否更新
- ✅ 学生端按需触发：学生在"我的成绩"页面点"刷新成绩"按钮，service 调 recalculate
- ✅ 管理员手动触发：管理端"批量重算"按钮可以一次性重算所有学生的 score_info
- ✅ 为后续消息队列预留扩展点（v4.2 不实现，但接口形态适合）

**为什么不在 application 通过时同步 recalculate：**

- ❌ 同步重算把"application 审核通过"和"成绩汇总"两件事捆绑在一起，application 事务容易因为 score_data 写入失败而回滚——审核员已经批准的申请因成绩聚合失败被"搁置"，体验差
- ❌ 单一用户的 application 可能被 PASSED 多次，每次同步重算 = N 次重算同一用户；解耦后只算一次最新状态

**触发点（本期实现）：**

1. **学生端"刷新成绩"按钮**：用户在学生端"我的加分"页面点"刷新"，触发 `POST /api/score/recalculate`（用户级）
2. **管理端"批量重算"按钮**：管理员触发 `POST /api/score/recalculate-all`（全体学生）
3. **管理端"单用户重算"按钮**：管理端用户详情页可单独触发某一学生

**MQ 扩展点（未来）：**

未来如果改用消息队列，recalculate 触发逻辑改为：

```
application.pass_application → 写 score_data + 发 MQ 消息
MQ consumer → 收到消息后调 ScoreDataService.recalculate(user_id)
```

这个改造把"application 主事务"和"成绩汇总"完全解耦：
- application 主事务只关心 score_data 流水
- 成绩汇总由 consumer 异步处理
- consumer 失败可重试，不影响 application 业务

**v4.2 本期不引入 MQ**——避免引入消息队列基础设施（Redis / RabbitMQ），先把解耦的 service 接口形态定下来。代码现状以"学生 / 管理员手动触发"实现。

**`user.score_info_dirty` 扩展点（本期不实现）：**

如未来改成"异步重算 + 学生端拉数据时检测脏位"的方案，在 users 表加 `score_info_dirty BOOLEAN DEFAULT TRUE` 字段：

- recalculate 成功后置 FALSE
- 学生调 get_summary 时若 dirty=TRUE 自动触发 recalculate 或返回 202 Accepted
- 后台 worker 扫描 dirty=TRUE 异步处理

本期 schema 不带这个字段。

## 四、完整业务流程（v4.2）

```
管理端配置（一次性）
  1. 配置 TemplateCategory 分类树（加分总计 → 学业/专长/劳动）
  2. 在叶子分类下创建 Template，可挂多个 Template（每个 template 独立按其 max_score 封顶，不相互影响；分类层级封顶由 recalculate 处理）
  3. 在 Template 下挂多个 Rule 与 Attribute（业务自行保证 rule 不冲突）

学生申请（草稿阶段）
  4. 前端加载 TemplateCategory 树，选择叶子分类
  5. 选择 Template，加载规则数据 → 前端本地实时计算分数（无需后端 preview 接口）
  6. 填写 proof 材料及分值（数量自定，**草稿允许 0 proof**，文件可空允许文字描述）
  7. 保存草稿 → ApplicationService.save_draft()
       └── 服务端调 ScoreCalculationService.calculate() 算出 apply_score 并快照固化
       └── 【草稿不强制 sum 守恒】草稿可以 0 proof / sum != apply_score，前端展示差额
       └── 【草稿阶段不写 application_operation】（按需启用 UPDATE_DRAFT 日志）
       └── 业务级唯一约束：同 (user, template) 不允许有另一条"活"申请
       └── 此时草稿可选择写一条 CREATE_DRAFT operation（**本期不写**，结构预留）
  7.5. 学生可重复保存草稿覆盖更新（DRAFT 状态）；也可删除草稿 → ApplicationService.discard_draft()
        └── DRAFT → DISCARDED（终态），写 DISCARD_DRAFT 操作日志

学生申请（提交阶段）
  8. 确认提交 → ApplicationService.submit()
       前置条件：status == 'DRAFT' + len(proofs) >= 1 + sum(proof_score) == apply_score
       └── 【强校验】proof 数量 ≥ 1 + sum(proof_score) == apply_score（DECIMAL 精度对齐，差 0.01 都不行）
       └── 整体替换 proof 列表：DELETE 旧 proof + INSERT 新 proof，**status 全部置 PENDING**
       └── application.status → APPLYING，写 SUBMIT 操作日志
  8.5. （可选）APPLYING 阶段学生主动撤回 → ApplicationService.withdraw()
        └── APPLYING → WITHDRAWN（终态），写 WITHDRAW 操作日志
        └── 业务动机：学生提交后发现填错，不必等审核员 REJECT

审批
  9. 审核员逐条审核 Proof → ApplicationService.review_proof()
       前置条件：application.status == 'APPLYING' + proof.status == 'PENDING'
       └── proof.status → APPROVED/REJECTED（**仅改 proof.status，不写 application_operation**）
       └── 不更新 gain_score（gain_score 在 PASSED 时一次性写为 apply_score）
       └── proof REJECTED 时 remark 可选，不强制（v4.2 放宽）
       └── 幂等：同一 proof 重复请求 → 409 Conflict
  10. 该申请下所有 proof 均为 APPROVED 时，审核员可投票通过 → ApplicationService.pass_application()
       前置条件：
         - application.status == 'APPLYING'
         - **所有 proof.status == 'APPROVED'**（即 COUNT(proof.status='PENDING' OR 'REJECTED') == 0）
         - (application_id, reviewer_id) 在 operation 上 PASS/REJECT 不存在（一人一票）
       └── UPDATE approved_count = approved_count + 1（SQL 原子 CAS）
       └── 若 approved_count == review_count → status → PASSED
                                          → gain_score = apply_score（同字段写入）
                                          → ScoreDataService.record() 写流水（**同一事务内**）
                                          → **不触发 recalculate**（已解耦到独立接口）
       └── 写 PASS 操作日志
  10.5. 或 审核员一票否决（veto）→ ApplicationService.reject_application()
        前置条件：status == 'APPLYING' + remark 非空 + 未投过票
        └── UPDATE status = 'REJECTED'（CAS）+ rejected_count += 1
        └── 写 REJECT 操作日志（remark 必填）
        └── 任何后续 PASS 请求被前置条件拒绝（status 已非 APPLYING）

再提交
  11. 学生修改被驳回的 proof → ApplicationService.resubmit()
       前置条件：status == 'REJECTED' + len(proofs) >= 1 + sum(proof_score) == apply_score
       └── 整体替换 proof 列表（**与 submit 完全同构**，不区分"删除哪些/新增哪些"）
       └── **不再限制** APPROVED / REJECTED proof——学生可任意增删改
       └── 所有 proof 重置为 PENDING（待新一轮审核）
       └── application.status → APPLYING，写 RESUBMIT 操作日志
       └── 【决策点】approved_count / rejected_count 不重置（保留历史投票）
       └── 如要修改 apply_score，重新生成新申请（new save_draft），当前 application 保留 REJECTED 终态

成绩汇总（**解耦到独立触发**）
  12. （PASSED 时**不**自动触发 recalculate）
       → ScoreDataService.record() 已写入 score_data，但 user.score_info 不更新
  13. recalculate 由学生端 / 管理端按需触发：
       13a. 学生点"刷新成绩" → POST /api/score/recalculate
            → ScoreDataService.recalculate(user_id) 同步重算 user.score_info
       13b. 管理员在管理端点"批量重算" → POST /api/score/recalculate-all
            → 遍历所有学生，调 ScoreDataService.recalculate
       13c. 管理员在用户详情页点"重算该学生" → POST /api/score/recalculate?user_id=?

  14. 前端展示 → ScoreDataService.get_summary(user_id) 读 score_info

操作查询
  15. 学生/管理员查"具体某次申请的完整审计"→ ApplicationOperationService.list_by_application()
  16. 学生/管理员查"哪些审核员投过票"→ ApplicationOperationService.list_votes()
  17. 学生/管理员查"该申请的所有 proof 通过/拒绝状态"→ 直接查 application_proofs.status
       （**proof 状态不再写 operation**，proof 表本身就是审计源）
```
